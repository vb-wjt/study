## 一、 liburing：一条没人声明的硬依赖，两次发作

### 1. 问题：包装成功、`initdb` 一跑就炸、界面照报成功

九个目标版本里，RHEL 9.6 与 9.8 两台机的装后取证是 **4/11 FAIL**：`initdb` 失败、数据簇是空的、5432 无人监听。但两台机的安装日志是 **0 条 `[ERROR]`、8 条 `[WARN]`，安装器界面报成功**——如果没跑取证脚本，会被当成装好了。

根因链条有三段，缺一段都不会出事：

- PostgreSQL 18 引入 io_uring，PGDG 的 el9 / el10 / deb 包**都带 `--with-liburing` 编译**，`postgres` 二进制的 `DT_NEEDED` 里有 `liburing.so.2`；
- 而 `liburing` 在 RHEL 9 属 **AppStream 而非 BaseOS**，最小化安装默认不装，**离线包里也没带**；
- 我们的安装脚本用 `rpm -Uvh --force --nodeps`，**把本可以干净拦住这件事的依赖检查关掉了**。

于是包照装成功、加载期才炸。一个反直觉的排查岔路：改 `postgresql.conf` 的 `io_method` **完全无效**——它的默认值 `worker` 本就不走 io_uring，缺库是**动态链接器在加载期**就失败，跟运行期走哪条 I/O 路径无关。

### 2. 定性：根因是宿主机状态差异，不是 OS 小版本差异

这是本条最值钱的一句。当时我们正在论证「为什么要逐个小版本实测」，手上的理由是「小版本之间有 ABI 硬边界」。liburing 这件事把理由换掉了：

**9.7 / 10.0 / 10.1 通过，不是因为那些版本没问题，而是那几台机上恰好装了这个库。** 任何一台没预装 liburing 的 RHEL 9 或 10 都会同样失败。RHEL 8.10 是唯一真正免疫的——el8 的包没开那个编译选项，这是**包的属性**，不是机器的属性。

后来还订正了一处：liburing 在 **RHEL 10.0 起已从 AppStream 移入 BaseOS**，这很可能才是 10.0 / 10.1 通过的真正原因，而不是"运气"。

> 这条定性直接改变了测试策略的依据。「宿主机状态差异」恰恰是**版本推导最覆盖不了的一类**——你可以从版本号推出 glibc 版本，但推不出「那台机装过什么」。

### 3. 选包：把「技术上兼容」换成「Red Hat 自己就在发」

三个目标小版本（9.6 / 9.7 / 9.8）要不要各带一个包？最终**统一取 `liburing-2.5-1.el9.x86_64.rpm`，一个文件覆盖三个版本**。

定案过程里有两个容易读错的地方：

**Red Hat 门户「Available From」表的正确读法是「取该频道里的最高版本」**，因为 yum 仓库存累积历史——一个 EUS 9.6 频道里同时躺着 0.7 / 2.3 / 2.5。按这个读法：9.6 发 2.5-1、9.8 发 2.12-1、9.0 / 9.2 只有 0.7-7（即 soname `liburing.so.1`，说明符号门槛在 9.4，我们最低目标 9.6 天然达标）。RHEL 9 的 EUS 只覆盖偶数小版本，所以表里没有 9.7（走主频道）。

**选 2.5-1 的硬理由是「它同时在 9.6 与 9.8 两个频道里」**——对两台机都是频道内包，这不是「技术上兼容」，是 Red Hat 自己就在发。

**两个陷阱构建**：`2.3-2.el9` 也在这两个频道里、装上 `ldconfig` 也有输出，**但缺 `LIBURING_2.5` 符号**，这个最阴；`0.7-7.el9` 的 soname 是 `.so.1`，根本对不上。所以**装前必须 `rpm -qp --provides … | grep LIBURING_2.5` 验一遍**，看版本号不够。

「每小版本各带一个」技术可行但**决定不做**：多出的符号 `postgres` 一个不用，引入零收益的版本跟踪负担，而且会与 PGDG 按小版本分包的语义混淆（liburing 的文件名本就只有 `.el9`，目录应按 `el9` / `el10` 分）。

### 4. 发行策略：再分发第三方构建物是合同与商标问题，不是许可证问题

这一节是纯技术之外的判断，也是我认为这条线最值得留档的一处。

包选定之后才发现真正的障碍不在技术侧：**把 Red Hat 的构建产物放进我们的安装介质再分发给客户，是合同与商标问题**。它和开源许可证**是两件独立的事**——liburing 本身是 MIT / LGPL-2.1 双许可，再分发是允许的；受限的是「Red Hat 构建的那个二进制」这个具体产物。

解法是**改用 RHEL 重建版的构建**：取 Rocky Linux 或 AlmaLinux 的 9.6 vault（两者实测均可达，文件大小分别 39037 B 与 38869 B），核对到**同一个 SRPM `liburing-2.5-1.el9.src.rpm`，Provides / Requires 与 Red Hat 构建逐项一致**。

两个注意点：

- **不要用 CentOS Stream 9**——它是上游滚动版、已经到 2.12，2.5-1 不在活跃仓库里。
- **签名 NOKEY 不阻止安装**——现有 PGDG 三件套同样是第三方签名，七台机全通过，这条已有先例。

顺带拿到一条**独立旁证**：Rocky 的 9.6 与 9.7 vault 都是 2.5-1、只有 9.8 是 2.12，与从 Red Hat 门户读出的结论完全一致——两条互不相关的证据链指向同一结果。

**最省事的来源其实是目标机自己的安装 ISO**（`AppStream/Packages/`），版本天然配套，还绕开再分发问题；已配本地仓库时一条 `dnf --disablerepo='*' --enablerepo=<repo> install liburing` 就够。

### 5. 工程护栏：单变量对照实验 + 一台干净机不可替代

修复走了三步，**缺任何一步都不足以把风险降级**：

**第一步（09-14，单变量对照实验）**：在 9.6 上**只**手工装上 Rocky vault 的 `liburing-2.5-1.el9`，其余包与流程原样重装。结果四条同向：

```text
装前 liburing 判读     MISSING / [BLOCKED]  →  OK / [PASS]
ldd -r 的 liburing 行  not found            →  /lib64/liburing.so.2
最小验证集              4/11 FAIL            →  8/8 PASS
安装日志 [WARN]         8 条                 →  0 条
```

两轮残留检查全部 `ABSENT`，排除了"靠上一轮残留蒙过"。

**第二步（09-17）**：代码合入——`deps/el9/` 独立目录 + `ldconfig` 探测已有就绝不覆盖 + `rpm -ivh` 干净装 + 装后补 `ldd -r` 真校验 + 卸载不删 liburing。

**第三步（09-18，不可替代的一步）**：**在 9.8 干净机上用新包验证**。9.8 是唯一一台**从未被手工补过库**的失败机——之所以刻意保留它不动，是因为**手工补过的机器无法区分「代码生效」与「残留库生效」**。这一步证明的是 `ensure_liburing()` 这段代码在起作用，不是人工痕迹。

实现上有两个约束值得记：

- **rpm 不能放进 `rpm/x86_64/rhel9.x/` 标签目录**——那里的 `set -- "$RPM_DIR"/*.rpm` 会把它扫进 `rpm -Uvh --force --nodeps` 一把装，等于强制覆盖 OS 基础库（波及 qemu / fio）。必须单独放 `deps/` 并用 `rpm -ivh`。
- **覆盖范围刻意不均匀**：RHEL 9 探测 + 带包自动装；**RHEL 10 只探测、缺库明确报 `[ERROR]` 但不带包**（BaseOS 只是概率高不是保证，而这条线的教训是「静默比失败贵」）；RHEL 8.10 免检。**探测与带包被有意拆开**——探测的代码成本与覆盖 9 还是 9+10 几乎无差，真成本在带包。

### 6. 第二次发作（Ubuntu）：一台"通过"的机器是被联网悄悄救的

09-21 同一条依赖在 Ubuntu 侧再次发作，而这一次的证据链比 RHEL 那次更有教学价值。

**两台 Ubuntu 24.04 Desktop 的单变量对照，起点相同、只差网络。** 离线那台：`postgresql-18` 因缺 `liburing2` 停在 `unconfigured`、`ldd -r` 报 `liburing.so.2 => not found`、initdb / 建簇 / 建库全线失败，**界面照常报成功**，运行期 `mtp.log` 刷了 47 次 `Connection to 127.0.0.1:5432 refused`。

而 09-11 被记为"通过"的那台，**装机时同样不自带这个库**——是 `install-postgresql.sh` 里那句 `apt-get install -f -y` 在 `09-11 14:28:03` **联公网**把包下下来装上的。三条独立证据：

```text
apt history.log              有 Commandline 原文
liburing2:amd64.list mtime   比装机日晚七个月
apt-cache rdepends --installed liburing2   唯一反向依赖就是 postgresql-18
```

**两份安装日志的差别只有一行**（`apt-get -f could not complete` 有没有出现）——只看通过那台的日志，根本看不出这个缺陷存在。而那句 `apt-get install -f -y` 的注释原文写着 `best effort, offline`。

顺带把「Ubuntu 是否自带 liburing2」用官方包索引**穷举证伪**：noble 的 `ubuntu-desktop` / `ubuntu-desktop-minimal` **零路径**通到 `liburing2`（能拉入它的只有 qemu / samba-vfs-modules / mariadb / mpd / plocate / bfs / libdex 这些非默认包），ISO 里选 Default 还是 Extended 都一样。而 resolute（26.04）则是 `sysprof` 进了 main 并被两个桌面元包 **Recommends** → `libsysprof-6-6` → `libdex-1-1` → `liburing2`，**所以 26.04 装完即自带**——这正是开发阶段长期用 26.04 却从未踩到的原因。

⚠️ **但那是 Recommends 不是 Depends**，`--no-install-recommends` 或精简镜像会断链 → **两个版本都得带包**。

### 7. 收口：同一份代码在两台机走相反分支，"见包就装"由此证伪

24.04 与 26.04 都做了**断网**验收，而两台走的是**相反的分支**：

- **24.04（装包分支）**：装前五项探测全空、判 `[BLOCKED]`；装后 8/8 PASS、`liburing.so.2 => /lib/x86_64-linux-gnu/`、`18 main 5432 online`、安装日志 **0 `[ERROR]` 0 `[WARN]`**（09-21 那轮是 8 条 WARN）。包来自离线 deb 有三条互相独立的证据：`apt history.log` 零条 liburing 记录、`apt-mark showmanual` 命中、`dpkg.log` 唯一一条 `install liburing2:amd64 <none> 2.5-1build1`。
- **26.04（跳过分支）**：自带 `liburing2 2.14-1`，日志打 `present (ldconfig); leaving the host copy alone`、**全程零 dpkg 输出**、装后 `dpkg -l` 仍是 `2.14-1`、`dpkg.log` 零条记录。

**26.04 那轮的判据选择是这条线最精细的一处**：最硬的证据是 **`apt-mark` 装后仍为 `auto`，不是版本号**。因为我们发给 26.04 的就是 `2.14-1`、与宿主同版——**版本号区分不了「跳过」与「装了同一版」**，但 `dpkg -i` 一旦跑过，标记必然翻成 `manual`。

**同一份代码在两台机走了相反分支，「见包就装」到此证伪**。只验 24.04 拿不到这个结论。

两个副产品：装前 `apt-mark showauto` 命中而 `showmanual` 不命中，**第一次从装前快照直接证实了 `sysprof → libdex-1-1 → liburing2` 那条 Recommends 链**（此前只有包索引推导）；顺带发现卸载脚本的 `PG_PKGS` 正则六个 deb 只匹配到四个、**漏删 `libpq5` 与 `libjson-perl`**——这是整个 deb 家族的问题，**RHEL 躲过是命名巧合不是设计**（PGDG 在 el 上把客户端库叫 `postgresql18-libs`、被 `^postgresql18` 一网打尽，deb 那边叫 `libpq5`）。

一处**自我更正**：曾写「2.14 链的是 26.04 的 libc6、两版不能共用」，**不成立**——两个包声明的都只有 `Depends: libc6 (>= 2.4)`。分版本发的真实理由是**包管理卫生**：外来包会挡住本机 apt 的后续安全更新。

### 8. 一处刻意不改：去掉 `--nodeps` 也没用

后来测到 **PGDG 的 RPM 元数据其实正确声明了这个依赖**（`rpm -q --requires postgresql18-server` 含 `liburing.so.2(LIBURING_2.0)` 与 `(LIBURING_2.5)`）。这把成因定到了单一处：**不是上游漏声明，是我们的 `--nodeps` 关掉了本可以干净拦住它的检查**——不加它，rpm 会直接报 `Failed dependencies` 并中止。

**但决定不改**，两个理由：

1. **去掉它并不能让安装器报失败**——`exit 1` 照样被上层 `|| log [WARN]` 吞掉，再叠加 IA 那边写死的 `; exit 0;`，净收益只是日志里多一条精确报错。
2. **三件套还链着 libicu / libxml2 / krb5 / ldap / libnuma 等十余个库**，它们在其它最小化安装上是否齐全**没有证据**。9.6 那台除 liburing 外全部解析成功，但那是一台机的证据。贸然去掉可能把「现在能装」变成「装不上」。

> **教训（三条）**：
> ① **`--force --nodeps` 是把上游已经做对的事关掉**。它在离线交付里很常见（为了绕过依赖顺序），代价是把「加载期才炸」换成了「安装期本可以拦住」——而前者的排查成本高一个数量级。
> ② **选第三方二进制时，「同一个频道里发的」比「技术上兼容」强得多**，而且要按符号验、不能按版本号验（`2.3-2.el9` 装得上、`ldconfig` 有输出、就是缺那个符号）。
> ③ **一台从未被人工干预过的机器，价值高于三台修修补补过的机器**。手工补过的环境永远无法区分「代码生效」与「残留生效」，这一步省不掉。

细节见 **`os-support/03` R-12 / R-13**（内部真源，不随本目录）、[`os-support/02` 附录 A.6](../1-foundations/os-dependency-contract-surfaces.md)、**`os-support/07` T-1 / T-2 / T-12**（内部真源，不随本目录）。

## 二、 OS 支持范围：把「测过几台」换成可论证、可复跑

### 1. 问题：「支持哪些 Linux」当时没有可对外引用的依据

进入 IT 阶段时要对外声明支持范围，而当时能拿出来的只有「装过几台，没出问题」。这不足以回答两个真实问题：**新出一个小版本要不要重测？** **某个版本通过了，能不能推导出另一个版本也行？**

### 2. 破局：三层分解 + 16 项依赖契约面 + 最小验证集

最终声明支持 **9 个版本**（RHEL 8.10 / 9.6 / 9.7 / 9.8 / 10.0 / 10.1 / 10.2 + Ubuntu Desktop 24.04 / 26.04，**逐个小版本对外声明，仅 x86_64**，ARM 不支持，Linux 默认 console 模式）。

论证结构是：

- **把系统分三层**——Java 应用层 / PostgreSQL 原生层 / OS 集成层。**只有 PG 原生层随小版本变**（PGDG 按小版本分包）；而**自带 Zulu JRE 21**（不是 Red Hat 的 OpenJDK，因此不读系统 crypto-policy）让 Java 应用层与 OS 基本解耦。
- **把「安装器对 OS 的依赖」显式化成 16 项契约面**，逐项判定「它随小版本变吗」。
- **测试分工**：每大版本一个全量基线 + 其余小版本跑**最小验证集 11 项**。

**把隐式依赖变成显式契约**，是这一节真正的产出。分层与矩阵只是结论，契约面才是可复用的方法。

### 3. 明写方法论边界：这是割集论证，不是全集

这一节是我认为整套论证里最该被后人先读的部分。论证的骨架是：

```text
PI 的代码是同一份  →  所以跨版本的差异只能来自 OS
                  →  所以穷举 OS 依赖面（16 项）即可覆盖差异
```

这是**割集论证**——它只覆盖「来自 OS 的差异」，**不是全集**。所以同时登记了四个已知漏洞（M-1 ~ M-4），并要求「凡引用范围裁剪结论时必须同读这一节」：

- **M-1** 穷举完备性是**假设**，不是证明——我们不知道有没有第 17 项契约面；
- **M-2** 「Java 层与 OS 解耦」只是**近似不是等式**——locale 与排序、文件系统语义、子进程行为等至少六类实则吃 OS；
- **M-3** 最小验证集只测「能装能起」，**不测「行为正确」**；
- **M-4** 对**非 OS 依赖**完全沉默。

M-4 后来被一个具体案例坐实：短信猫插件（跑在 `tafsvc` JVM 内，用 `jSerialComm`）在 Linux 上因服务降权而失效——实机确认 `dialout` 组**成员为空**、`/dev/ttyS*` 是 `root:dialout 660`、服务账户可写为 NO，即**除 root 外无任何账户能读写串口**。这是个**运行期功能回归，与安装成功无关**，11 项验证集完全不覆盖。连带把内核版本从「运行期基线、不用于范围决策」提升为**硬件功能的首要变量**。

### 4. 两条承重论据倒掉：一处文档笔误，一处符号版本

论证做完之后，**两条最硬的论据先后被自己推翻**。

**其一：「RHEL 9 小版本间 glibc 发生过 rebase（9.7=2.34 → 9.8=2.39）」是错的。** 9.8 release notes 第 10 页写的 2.39 是 **Red Hat 的文档笔误**——同一节里 Annobin / GCC / Binutils 全是 RHEL 9 的旧值，而 2.39 是 RHEL 10 的数。实测那台机内核 `5.14.0-687.5.3.el9_8` 与 9.8 自述精确吻合，而 `ldd --version` 给的是 **2.34**。

**其二：「9.6 ↔ 9.7 之间有 OpenSSL 硬边界」也站不住。** 9.7 / 10.0 / 10.1 的 `postgres` 都只要 `OPENSSL_3.0.0`，而 RHEL 9 内部从 3.2.2 到 3.5 全是 `libcrypto.so.3`、都提供该符号。

实测下来，**RHEL 9 三个版本的 glibc / libicu / libstdc++ / OpenSSL soname 四项全同，内部没有 ABI 硬边界**；真边界在大版本之间（RHEL 10 的 `postgres` 要 `GLIBC_2.38`、libicu 从 so.67 到 so.74）。顺带实证了**单向 ABI 兼容**：10.x 的 `postgres` 装不进 9.7（只有 2.34），反向可以。

**关键在于倒掉之后怎么处理：倒掉的是论证，不是做法。** 按小版本分包、包标签校验、逐小版本实测三项**全部保留**，只是「逐版本实测」的理由从「ABI 边界」换成了「宿主机状态差异」——而后者恰恰是推导最覆盖不了的一类（见第一章第 2 节）。

### 5. 把论证做成可执行脚本：五档判读与十个真 bug

论证如果只是文档，下一个版本还要从头来。所以做了两个 bash 脚本（共 1,737 行）：

- **装前体检**：IA 的 OS 白名单正则**原样重放**自测 + A/B/C/D/E 五组采集，与内置的 **9 版本 × 8 组件预期值表**自动比对；
- **装后取证**：三项装后指纹 + **最小验证集 11 项里 8 项的自动判读**，逐项给 PASS / FAIL / MANUAL / UNKNOWN。

判读分五档——`OK` / `MISMATCH` / `INFO_DIFF` / `UNVERIFIED` / `RECORDED`——对应证据强度的四档出处，**后来加了第六档 `FLOOR`（下界比对）**。`FLOOR` 的由来值得记：Ubuntu 的 `kernel` 与系统仓库 PG 版本在**同一 LTS 内向前滚动**（24.04.1 的 GA 内核 6.8 → 24.04.3 默认 HWE 6.14），拿 release notes 的 GA 值做等值比对**必然翻红**，这属于**判读档位设错，不是数据错**。比较要用 `sort -V`，`sort -n` 会把 6.14 当小数。

脚本迭代过程中**修掉了十个会造成误判的真 bug**，其中前四个每一个都足以让一轮验证的结论作废：

1. **日志候选 glob 匹配到 `chrome_installer.log`**，并据此报「第 11 项 PASS，零 ERROR 零 WARN」——**拿一个无关日志判 PI 通过**；
2. 串口 mode 是 666（世界可写）时，只看组成员资格会**误判为不可写**；
3. **`tafdb` 是 oneshot 薄别名**（真实 PG 单元在 `Requires` 里），跑完转 `inactive` 属正常，按真服务判会**稳定误报** FAIL；
4. **Ubuntu 的 `postgresql` 伞单元按设计就是 `active (exited)`**，查它等于没查，那一项形同虚设；
5. `grep -c` 数到 0 时**退出码为 1**，导致写出 `0 N/A` 双值；
6. `dpkg -l` 的 Name 列对 Multi-Arch 包带 `:amd64`，`^libpq5$` 匹配不上 → **误报 Ubuntu「PG 包不齐」**；
7. Ubuntu 默认无 binutils，`strings` 不可用导致白丢基线；
8. udev 检测把 ModemManager / snapd **自带**的规则算成「人为规避」；
9. 预期值表里某一行**从未被 judge**、对应探测在干净机上整段跳过——表里 9 行是死数据；
10. **强制访问控制检测在 Ubuntu 上从未被验过，而且不是静默跳过而是会误报**——procps 的 `label` 字段读 `/proc/<pid>/attr/current`，AppArmor 无约束时填的是**非空**字符串 `unconfined`，于是被判成「偏离基线」。改法是先读 `/sys/kernel/security/lsm` 认 LSM 再分叉。

顺带把一个横跨三代策略包的结论坐实了：RHEL 上 `selinux-policy` 3.14 / 38 / 40 / 42 **全部**把 PI 的 java 进程放在 `unconfined_service_t`，Ubuntu 侧 AppArmor 也无 profile 命中 PI → **「强制访问控制不是障碍」从单点观察升为稳定结论**。

### 6. 终局的一处退步：人工验证不可 diff

九个版本的**终轮**验收**没有脚本结果文件**——证据是人工功能验证，不可 diff。代价很具体：**RHEL 10.2 与 Ubuntu 26.04 至今没有完整库基线**。这一点已经写进结果目录 README 的开头做警示，**防止后人从「目录里没有 10.2 的文件」误推「10.2 没验过」**。

但同一轮人工验证带来了一条**反向结论**，值得写进交付规程：

**人工功能验证正面否证了 R-1 的危害形态。** R-1 的危害是「界面报成功、库其实是死的」，而采集信号与备份**必然读写业务库**，库不可用则必然失败。也就是说——**只要验收环节包含一次真实功能确认，R-1 就无法把坏机器放过去**。这比在安装器里加硬失败便宜得多，也不必碰 IA 工程。

⚠️ **但前提是验收流程必须真的包含功能确认**，不能退回「看界面报成功就签字」。这是一条**流程约束换技术修复**的决定，它的有效性依赖于流程被真正执行。

> **教训（三条）**：
> ① **支持范围要给出论证结构，并且明写论证的边界**。写下「这是割集不是全集」和四个已知漏洞，比多测三台机更有价值——因为它让引用这个结论的人知道自己在引用什么。
> ② **论据倒掉时，先分清倒的是论证还是做法**。两条承重论据全没了，但三项做法一项没改，只是理由换了——如果当时把做法也一起改掉，就会因为一个文档笔误而丢掉正确的测试策略。
> ③ **把论证做成脚本，脚本本身会暴露论证的漏洞**。那十个 bug 里有四个是「验证工具在说谎」，靠读文档永远发现不了；而第九个（表里的死数据）说明**没被执行过的判读逻辑等于不存在**。

## 三、 `.properties` 编码链：安装器全程零报错，管理员账号成砖

### 1. 问题：输入正确、落库乱码、入口彻底进不去

安装面板里输入中文管理员名（`吴吴吴`），面板内显示正确、安装日志里的字节也是干净的 `E5 90 B4`，但装完之后**管理员登不进去**。

**危害形态是「砖」不是「校验失败」**：落库的乱码里夹着 **`U+0090`**——一个不可打印的 C1 控制字符，**这个用户名物理上无法用键盘输入**。叠加首登自带的锁定策略（5 次 / 120 分钟），管理员入口彻底进不去。而**安装器全程零报错**，又是一次 R-1 形态。

### 2. 定位：字节形态唯一指向 ISO-8859-1

链路是五段，坏在第二段：

```text
IA 面板输入「吴吴吴」                                        正确
  → ASCIIFileManipulator 把它原样写成 UTF-8 裸字节进 .properties
  → Spring Boot 读 .properties 固定用 ISO-8859-1（Java Properties 规范）
  → @Value 拿到「å<U+0090>´」×3
  → createBuiltinAdminIfAbsent() 原样落库
  → isAdminUsername() 的精确 equals 永假
```

**字节证据把范围收敛到了「进业务逻辑之前」**：安装日志里有干净的 `E5 90 B4`、没有 `C3 A5`；而 `mtp.log` 里有 `C3 A5 C2 90 C2 B4` ×3、**全文搜不到 `E5 90 B4`**。

**而这个字节形态唯一指向 ISO-8859-1**——如果是 GBK 误读，`吴` 应该是 `CE E2`，对不上。这一步排除了「某处按 GBK 解码」这个竞争假设。

**关键依据让修法从「发明机制」降为「照抄已有做法」**：同一次安装产物 `installvariables.properties` 里，同一个值是 `PI_ADMIN_USER=\u5434\u5434\u5434`（纯 ASCII）——**IA 走 `Properties.store()` 的那条路径是会转义的**。问题不是「IA 不会转义」，而是**同一个安装器内两条写入路径不一致**。

### 3. 第一次破局失败：IA 的转义与 Spring 的反转义正好抵消

第一版方案是「在模板里放转义后的 token，让 IA 替换进去」。代码写完、单测过了，实机装出来 **DB 里存的是字面量 `\u5434…`**——输中文登不上，输字面量能登上。

**根因单点：IA 的 `ASCIIFileManipulator` 在替换变量时把反斜杠翻倍。** 文件里是 `\\u5434`，Spring 正确地把 `\\` 还原成一个 `\` → 得到字面量。四条证据定责：

```text
① installvariables.properties 的原始字节反推出 IA 侧的值完全正确（单 5C vs 双 5C 5C 可区分）
② 反编译 Spring Boot 的 OriginTrackedPropertiesLoader$CharacterReader.readEscaped()
   确认 'u'(117) → readUnicode() 会还原
③ 后端无任何自定义 EnvironmentPostProcessor / PropertySourceLoader
④ 管理员读配置文件原始字节，该行反斜杠计数 = 10（应为 5）
```

**而这个翻倍是承重行为、没有开关。** 同一个文件里 `logging.file.name` 替换后是 `C:\ProgramData\…\mtp.log`——不翻倍就会被 properties 的转义规则吃掉反斜杠。所以也**无法预先减半来抵消**。

进一步查证：**翻倍是按 `.properties` 后缀触发的，不是节点属性 → 所以在 Designer 里也找不到开关**。硬对照是 `TAFsvc.ini` 那个节点——它与我们这个节点的 `substituteIAVariables` / `textOptionsType` / `fileTargetType` **逐项相同**、`desiredFileEncoding` 两边都未设（全工程 29 个同类节点无一设置），装出来却是**单**反斜杠，**唯一的变量是目标文件后缀**。Spring 侧同样堵死：`PropertiesPropertySourceLoader.load()` 写死 `Charset=null`，整个 jar 里只有 7 个 `spring.config.*` 键，**没有任何配置项能指定 `.properties` 的读取编码**。

**最准确的表述是：IA 的转义与 Spring 的反转义正好互相抵消，整条管道对反斜杠是恒等变换**——送进去什么字面量，出来就是什么，Spring **永远不会真的执行一次 `\uXXXX` 解码**。这是原理上的死路，不是配错了。

一个附带收益：严重度**降级**了——从「含不可打印字符、账号成砖」变成「纯 ASCII 字面量、照着输能登录」。所以那两次提交**保留不回退，也不阻塞发布**。

### 4. 第二次破局：铺完文件后由自定义动作改写那一行

三条出路里选了 B：**等 IA 把文件铺完，再由一个自定义动作去改写那一行**。

被否决的另两条：A = 让自定义动作直写另一个配置文件（IA 零改动，但配置文件分裂 + 依赖 Spring 的 profile 优先级）；C = 改后端读 Base64 或换 yml（最稳，但跨仓库，影响面含数据库与 TLS 口令密文）。

**选 B 的决定性依据是「用户可以直接用 IA Designer 完成」**——B 原本唯一的减分项「手改 XML 有 objectID 被剥离的风险」随之消失，换来配置文件不分裂、不依赖任何隐式优先级。

实现要点：ISO-8859-1 字节透明读写、**下标切片只换目标行不用正则**、锚定行首、幂等、复用已有的转义函数，配 7 例单测。**模板里的 token 仍然留着当兜底**——动作没跑成就退回「字面量、照着输能登录」，不会把安装搞失败。

一处**被放弃的过渡方案**值得记：曾想中转期把 IA 节点的类名先指向另一个已存在的动作类，**已放弃**——那个类跑两遍**不幂等**：第二遍会用新密码重新生成 `keystore.p12`，而配置文件里已经写入了第一遍密码的密文 → **8443 起不来且全程无报错**。

### 5. Linux 分支：Windows 掩盖了一个一直都在的缺陷

Windows 实测通过后，同一个包在 RHEL 9.8 上**四条判据全部反向命中**：落盘是双反斜杠、`mtp.log` 里 UTF-8「吴」0 次而字面量 162 次、动作日志说「文件还不在那儿」、系统可用但认到一个 36 字符的字面串。而**安装日志 0 Warnings、健康检查 UP**——「失败非致命且静默」的代价：不盯字节根本发现不了。

**根因不是动作自诊断说的「排序问题」，是路径。** 配置模板的 `InstallFile` 挂在一个 `GhostDirectory` 下，后者的 `destinationFolder` 是 `UserMagicFolder1MF` → **Linux 上 `$USER_MAGIC_FOLDER_1$` = `/etc/opt/pi`，在安装根之外**；而动作把路径**拼**成了 `$USER_INSTALL_DIR$/config`。这在 Windows 上恰好同指一处、在 Linux 上扑空。

**缺陷一直都在，只是 Windows 掩盖了它。**

修复三处：① 新增 `resolveConfigDir()`，**先问 IA 要 `$USER_MAGIC_FOLDER_1$`**、取不到才回退旧猜法（先例：同工程另一个动作早就在用 `substitute("$USER_MAGIC_FOLDER_4$")`）；② 越界屏障的锚点从「安装根」改成「配置目录」——锚在安装根会把合法的 Linux 目标判成路径逃逸；③ 「文件不存在」的措辞补上实际查找的目录，不再把结论写死成「排序不对」。

⚠️ **重打包后 Windows 必须回归**，判据是日志里**不出现**那句回退提示——否则等于白改（回退分支会让 Windows 无论如何都通过）。

### 6. 判读：哪些日志行不能当「中文名测过」的判据

RHEL 复测通过时，三项字节计数与首测**整齐反转**（UTF-8「吴」47 / `C3 A5` 0 / 字面量 0 对上首测的 0 / 0 / 162）。**最硬的一条证据是会话超时事件里的 `"username":"wu吴一二三"`**——那是登录态才会产生的记录。

落盘那一行没有直接取到（需要 root），但**反推是封闭的**：双反斜杠会被读成字面量（实测 0 次）、裸 UTF-8 被误读会出 `C3 A5`（实测 0 次），两条退化路都排除了。

这一轮还多一条 Windows 拿不到的证据：中文名是在 **Delete All 之后**仍然正确的——那一轮库被重建（前后资源 `_id` 集合**零重叠**），所以管理员名只可能来自本轮新落盘的配置，**排除了「读到旧库残留」**。

⚠️ **而有一条日志行不能当判据**：动作打印的 `wrote the escaped …` **不区分中英文**——同一天 Ubuntu 三轮全用 `admin` 也逐轮打出该行。它只证明动作**找到了文件**（即路径修复生效），不证明中文处理正确。

**机制归属最后是靠一处大小写反差锁定的**：同一份 `installvariables.properties` 里，`PI_ADMIN_USER` 是单 `\u` + **大写** hex（IA 的 `Properties.store()` 转义真实中文），而我们那个变量是双反斜杠 + **小写**；**落盘行是单反斜杠 + 小写** → 只可能出自我们自己的转义函数（`Character.forDigit` 产小写），不是 IA 替换的产物。

> **教训（四条）**：
> ① **同一个进程内两条写入同类文件的路径，编码行为可能不一致**。查的时候先找「有没有另一条路径把这件事做对了」——本例正是这样把修法从「发明机制」降为「照抄」。
> ② **两个各自正确的转义/反转义叠起来可能是恒等变换**。这类问题不会报错、不会有日志，只能靠数字节发现。
> ③ **custom code 碰 IA（或任何框架）铺下来的文件，要向框架「问」路径，不要按自己熟悉的平台「拼」路径**；越界检查的锚点要跟着落点走。
> ④ **诊断措辞不要把结论写死**。那个动作打的是「排序还没到」，而真相是「路径找错了」——错误的自诊断把排查方向带偏了一轮。

细节见 **`os-support/07` T-9**（内部真源，不随本目录）。

## 四、 IA 变量替换吞掉用户输入：从截断到变量注入

### 1. 问题：32 字符落盘变 19 字符

用户输入 `!@#$%^&*()_+!@#$%^&*()_+!@#$%^&*`（32 字符），配置文件与数据库里都是 `!@#%^&*()_+!@#$%^&*`（19 字符）。

先排除了自己家的代码：那个转义函数对 `0x20-0x7e` 原样透传、**只会让串变长**，所以值在它拿到之前就坏了。

### 2. 定位：第 1 与第 2 个 `$` 无条件配对

`ip.substitute()` 是一个**模板展开**接口——它会对展开结果继续解析。而 `VariableStringResolver.find(String,int)` 的实现就是 `indexOf($)` 找到一个、再 `indexOf($)` 找下一个，**第 1 与第 2 个 `$` 无条件配对**当成变量引用，未知变量解析为空串 → 整段 `$%^&*()_+!@#$` 被删掉。

**触发条件可以定量**：「用户名含 ≥2 个 `$`」**既必要也充分**，受损段数是 `floor(n/2)`，剩下的单个 `$` 原样保留（3 个 `$` 正对应本例）。

**而且不止是删除**——两个 `$` 之间若碰巧是一个真实的 IA 变量名，替换进来的是**那个变量的值**（如 `a$PROFILE$b` → `aprodb`）。**性质上这是变量注入，不是截断。**

### 3. 排除竞争假设：按 `%` 配对得到的串不符

这一步是本条最该留的方法。**逐字节验证**：删掉预测区间之后的结果与实际落盘值**完全相等**。然后**算竞争假设**——如果是按 `%` 配对（比如某处走了 cmd 的 `%VAR%` 展开），得到的应该是 `!@#$^&*()_+!@#$%^&*`，**与实测不符，排除**。顺带确认用户名不流进任何 `.bat`，不存在 `%VAR%` 展开的可能。

**有一个能解释现象的假设不等于定位完成**，还要把能解释同一现象的其它假设算出来、并证明它们对不上。

### 4. 修法是换 API，不是改 IA

`IAProxy` 上同时有 `substitute(String)→String` 和 `getVariable(String)→Object`。后者是**对象通道、原样返回**——旁证是工程里早就有代码用它往返过一个 `Map`，**返回类型是 `Object` 本身就证明它不做字符串处理**。

所以修法是新增一个读原始值的方法，把三处「读用户输入」的调用换掉：管理员用户名 ×2 + **数据库密码**（含 ≥2 个 `$` 的密码同样被截断）。

一处**刻意未改**：另一个校验器读的变量是**按引用存**的，单独换 API 只会拿到字面量 `$PI_ADMIN_NAME$` → **单独改必坏**。这暴露出一个更深的问题：**那个校验器当时校验的是被破坏之后的字符串**，所以 1-32 的长度上限可以绕过（输 40 字符夹两个 `$`，缩水到 30 就过了），落在被吃区间里的 `' " | /` 也逃过检查。

### 5. 反编译定到单点：`passByValue=true` 时那个取反

诊断阶段先用三通道测量确认了**坏在存入、不在读回**：

```text
getVariable  PI_ADMIN_1     = 32   ← 面板原始字段
getVariable  PI_ADMIN_USER  = 19   ← 归一化副本
substitute   PI_ADMIN_USER  = 19
```

然后反编译定到单点：`EditMultipleVariables.setVariables()` 在 `passByValue=true` 时执行 `substitute(rawValue, !isSubstituteUnknownVariable())`——**注意那个取反**。而 `VariableManager.substitute(s,z)` 里，未知 token 的处理是「`z=false` 原样保留、`z=true` 直接删」。

**所以 IA 侧的改法就是把那两个节点的「Do not substitute unknown variables」勾上，不用改任何代码。**

### 6. 收口：让校验端与落盘端读同一个原始字段

两条残留（长度上限可绕过、已知变量注入）的根子在于「**校验端读的是归一化副本，落盘端读的是另一个串**」。所以收口做法是**让两端读同一个原始面板字段**——把校验器的输入指向面板原始变量，两个消费端都改走同一个读取函数。

产品最终批准**禁 `$`**（校验器正则加 `$`），代价是那个 32 字符标点名会被拒。这里有三处工程细节值得留：

**其一，英文文案改错了地方。** 英文原文在 `.iap_xml` 的 CDATA 里，而 `custom_en` 是**构建产物**——只改后者不生效。这是本批唯一一次真正的返工。

**其二，「被拒时原样回填」走了两版。** 第一版写面板原始变量，实机无效；反编译 `CreateDialog.getValuesFromVariable()` 才确证**面板回填读的是面板自己的那个变量**（`substitute` 之后按带引号的 CSV 拆分，空串则不回填），改写落在它上面**并自带引号**才生效。顺带坐实了「复合变量确实带引号存」——实测日志里那行 `PI_ADMIN="abc"` 是这个护栏成立的前提。

**其三，GUI 与 Console 是两套类。** GUI 走 `CreateDialog`（变量名不带 `$`），Console 走 `GetUserInputConsole`（带 `$`）；**Console 用 `setNumberedNotQuotedLiteralVariables` 存原始串、不过 `substitute`，而且完全不回填**（整个类库里只有两处调用 `getValuesFromVariable`，都在 GUI 侧）。结论：**禁 `$` 在两侧都成立，但「原样回填」只有 GUI 有**——所以那条验收项在 Console 上不适用。这个判断是先反编译推出、再实机确认的。

### 7. 改不掉的残留：纯展示吞噬

同一个 IA 内建摘要面板对 **`< > &`** 也有吞噬——`<` 后跟字母会吃掉一整段、`<>` 相邻时两者皆丢、`&xxx;` 实体样式被转换，而孤立的 `>`、`&` 及其余标点正常。成因是 IA 的 GUI 用 HTML 标记渲染字段值。

**但它与 `$` 截断性质不同：值落盘完好，只坏显示。** 已评估**只登记不修复**；若将来收口，与禁 `$` 用同一处正则把 `< > &` 一并拉黑即可。

另有一处「界面显示 ≠ 实际装入」也归入已知并接受：含 `$` 的名字在校验失败回弹时，输入框会变成解析后的值（IA 面板自身行为，**而且会真的改掉提交值**），摘要面板对已知变量恒显示解析值。

> **教训（三条）**：
> ① **`substitute()` 只用于自己写的模板串；凡是读用户输入，一律用 `getVariable()`。** 这是本章唯一需要记住的一句话——模板展开接口会对展开结果继续解析，把用户输入喂进去等于允许用户注入模板语法。
> ② **有一个能解释现象的假设，不等于定位完成。** 要把竞争假设算出来并证明对不上（本例是 `%` 配对）。
> ③ **「校验端和落盘端读不同的串」是一类结构性缺陷**，它会同时制造「校验绕过」和「值被改坏」两个症状，而且这两个症状看起来毫不相关。修法不是给校验加规则，是让两端读同一个源。

细节见 **`os-support/07` T-15**（内部真源，不随本目录）。

## 五、 修好 A 激活了潜伏的 B：证书被连带删

### 1. 问题：Delete All 终于能删了，但装完 8443 起不来

重装弹窗改造（Linux 上「Yes = 删除」原本是个坏分支，而它正是默认项）落地后，RHEL 9.8 上第一次真正跑通 Delete All——**参数链通了**（日志里 `delete_prior_data=1` + `dropping existing cluster before re-init` + `CREATE DATABASE`），**一条悬了整轮的风险由此排除**。

但同一轮里 `mtp.log` 开始反复刷：

```text
Could not load store from '/opt/.../data/certs/keystore.p12'
  → FileNotFoundException
```

tafsvc 崩循环、8443 起不来，**而且该环境无法自愈，只能重装**。

### 2. 根因：顺序 + 一行平台赋值

删除动作要删的是整棵 `$USER_MAGIC_FOLDER_2$`，它排在「把证书写进 `$USER_MAGIC_FOLDER_4$/certs` 」那个动作**之后**（两平台同序）。而「Special Directories」节点里：

```text
Windows：$MAGIC4 = $USER_INSTALL_DIR$
Linux  ：$MAGIC4 = $MAGIC2$        ← 两者重合
```

于是 Linux 上刚生成的 `keystore.p12` / `core-trust.jks` 被连带删掉，IA 事后只重建了一个空 `certs/`，而配置文件里 `{cipher:tls}` 的密码还在 → **装完即不可用**。

**Windows 躲过纯属两个目录不重合，不是有门控挡着**（该节点根本没有平台门控）。而改造之前，Linux 上那个条件因为取不到有效值、规则恒假，**这个删除动作从未真正执行过**。

**这是一次典型的「修好 A 激活了潜伏的 B」。**

排查中有一条通用机制被查实：执行顺序的真源是宿主节点下的 `visualChildren`，`installChildren` **只管打包归属**。排查时曾被 `installChildren` 里的序号误导（那里 Delete 排第 21、写证书排第 29），而实际执行顺序**恰好相反**。

修法是**上移删除动作、不能下移写证书的动作**（紧跟其后有四处文本替换在消费它设置的密码变量），落点特意选在中止回滚动作之后，以免出现「先删数据再中止」。

### 3. 第二次返工：两个 `GhostDirectory` 不等价

重打包后三个平台都反馈「选了 Delete All 但数据目录还在」。**根因就是上一步那次搬家本身**——判断它「落点安全」是错的。

两个容器在 Designer 的树里看着可以互换，结构上不是：

```text
容器 A：直接定义在 OSHost 的 visualChildren 下，全文零 refID
容器 B：定义在 Installer 的 classpath 属性下，靠一个 refID 才接进 OSHost
```

**挂进容器 B 的 action 不会被调度**——这正是既有文档记过的「双重 parent 引用 → 执行引擎不可测的锁定或跳过」，这次踩的是「跳过」那一侧。

**证据是一对严丝合缝的对照**：搬家**前**的 RHEL，Delete All 那轮日志有 `Delete Folder: Source:data`、同一晚 Keep 那轮**零条**——动作确实会跑，且只在该跑的时候跑。搬家**后**的 Windows，547 KB 的 Delete All 日志里「安装文件」「执行命令」上千条、**「删除文件夹」零条**，数据目录整个活下来，`PG_VERSION` 还在于是 `initdb` 的 gate 也跟着跳过、旧簇原样复用。

### 4. 一次假零命中：跨语言日志

中途一度误判成「规则恒假、从来没执行过」，**已推翻**。错因有两个，第一个更值得记：

**拿英文 `Delete Folder` 去搜中文 Windows 日志**（条目名实际是「删除文件夹」），得了一个**假零命中**，并据此下了结论。第二个是把变量转储里显示的字面量当成「规则读不到值」，而实际两平台机制相同，且 RHEL 那条日志直接证明规则能为真。

### 5. 收口：改在条件本来就能解析的地方删

**决定不把引用挪回去**——挪回去等于把「证书被删」这个故障原样放回来（那个动作要删的整棵目录，在 Linux 上正是刚写完 `keystore.p12` 的地方，在 Windows 上还含 `log/`）。

改成在**条件本来就能解析的地方**执行删除，三处改动：

1. **Windows 的 `initdb` 命令前加一段独立的前置删除**——原有的 `rmdir` 一直都在，但被包在 `if not exist PG_VERSION` 里，**恰好在它唯一该生效的 Delete All 场景下不可达**；删掉目录后 `PG_VERSION` 随之消失，后面两个原有 gate 自己就会走 `initdb`，其余一字未动。
2. **ZE 的暂存数据两平台都改成丢弃而非恢复**——ZE 按 host 去重，恢复旧库会把新建设备映射到旧 id，而 ZE 对已是 NORMAL 的设备不再推「通讯恢复」，设备就一直转圈到手工重启服务（两个发行版都复现了）。
3. **摘掉那个节点在执行树里的最后一个引用**，让「退役」成为显式决定，而不是挂错地方的副作用；定义留在原处以免构建期被优化掉。

> **教训（三条）**：
> ① **凡是让一个「一直为假」的条件变成可以为真，都要把依赖它的所有节点列一遍。** 新增逻辑有人审，**被顺带唤醒的旧逻辑没有**——这是本项目里最值得泛化的一条。
> ② **四条静态自检全过 ≠ 动作还活着。** 唯一判据是装完之后去日志里数它的执行条目。这次静态检查（ID 唯一性、XML 良构、引用总数 delta 为 0）全部通过，而动作根本没被调度。
> ③ **跨语言日志做「零命中」判定前，先确认条目名的实际语言。** **零命中是最容易造假的一类证据**——它看起来像铁证，实际上任何拼写、语言、大小写、时间窗口的偏差都会产出它。

细节见 **`plans/reinstall-data-prompt.plan.md`**（内部真源，不随本目录）、**`os-support/07` T-8**（内部真源，不随本目录）。

## 六、 结构性不对称：一半固定路径、一半跟随路径

### 1. 问题：装完能登录、设备齐全、就是没人采集

Linux 上换安装目录重装之后：能登录、通讯状态正常、设备列表齐全，**唯独没有任何数据被采集**。

**判据只有一行**——伴生引擎日志里的 `Singleton Device(SNMP) count=0`。

### 2. 根因：密钥的生命周期考虑过，业务库那半没跟上

Linux 上 PostgreSQL 走**系统集群**（固定路径 `/var/lib/pgsql/18/data` 或 `/var/lib/postgresql/18/main`），而 certs / system / log / 伴生引擎的暂存库全都**跟着 `$DATA_DIR`**。

**一半固定、一半跟随**。于是任何「`$DATA_DIR` 换了或没了、但集群还在」的时刻，两半就脱节：PI 那边留着设备记录，伴生引擎那边拿到一个空库。

触发入口三个，方向无关：默认 → 自定义、自定义 → 默认、以及**原地重装前手工 `rm -rf $DATA_DIR`**（最后这条概率最高，危害此前被低估）。

**最值得记的一点是：这件事当初被明确考虑过，只是考虑了一半。** 卸载脚本里写 nonce 那段的注释原话就是：

```text
so it survives this uninstall AND a reinstall to a different dir
```

同一次卸载写的三行暂存数据都标着 `kept for same-host reinstall`，**落点却一半在 vault、一半在 `$DATA_DIR`**。也就是说，**密钥的生命周期边界划对了，业务库那半没跟上**。

### 3. 修法与守卫

把暂存库从 `$DATA_DIR/ze-data-cache` 挪到 `/var/lib/vertiv/ze-data-cache`——与两个 nonce 平级，但**不塞进 `machine-secrets`**（那是密钥库，这是业务库，两者的备份与清理策略不同）。

随之加两个守卫，因为脱离 `$DATA_DIR` 之后它会**独立存活**，从而产生一个反方向的不一致：

- **无集群守卫**：暂存库可能被恢复到一个全新的 PI 上；
- **老位置回退**：过渡期兼容，现场都过一轮新包后可删。

**Windows 结构上不存在这个问题**（PG 数据与暂存库同在一个目录下，换路径一起消失 = 干净全新安装），零改动零回归。

一个连带的**决定不改**：弹窗上把 `(not detected)` 改成 `(deleted)` 已评估后放弃——**安装器只知道「找不到」，不知道「被删了」**。而 `/var/lib/pgsql` 独立挂盘未挂载时，显示「已删除」会误导用户选 Delete All，**把一个可恢复状态变成不可恢复**。

> **教训（两条）**：
> ① **同一次操作里若有一组数据要「跨越某个边界存活」，必须把这组数据列全、落点统一。** 本例的失败不是没想到，而是想到了一半——三行暂存数据里两行落在正确的地方，第三行没跟上，而代码注释还写着正确的意图。
> ② **「一半固定路径、一半跟随路径」是一个可以主动排查的反模式。** 凡是系统里有两类存储、其中一类的位置由用户输入决定，就应该问：它们在「用户输入变了」的时刻会不会脱节。

细节见 **`os-support/07` T-13**（内部真源，不随本目录）。

## 七、 校验前移：只挪中间一段必坏

### 1. 问题：两个方向相反、都不可接受

把三组数据库参数校验复制进两个安装分支之后，**位置是对的**（实机确认「DB 面板点下一步当场拦截，不进下一页」），**但校验读的变量在那个时点还没赋值**。后果分两个方向，都不可接受：

- 两个口令变量初始值为**空** → **口令校验必然失败，那个分支根本装不进去**（输合法口令也拦）；
- 两个端口变量在分支之前已被赋了默认值 5432 / 8443 → **端口校验永远通过，填 `abc` 也不拦**。

**后者比前者隐蔽得多**——静默假通过不会有人报障。

### 2. 根因：「面板变量 → 归一化变量 → 校验」是三段式

面板输入先落到分支私有变量，再由分支内两个归一化动作转成共享变量，校验读的是共享变量。而**归一化排在第 9 / 10 位，复制进来的校验组排在第 3 / 4 / 5 位**。

修法不需要新建任何节点：两个分支各做两步——把含绑定 IP 的那个归一化动作从第 9 位拖到第 3 位（面板之后、校验之前），然后在它与留在原位的那个之间**对调条目**，让一个专管数据库面板、一个专管管理员面板，各自紧跟自己的面板。

⚠️ **不能把第 9 步整体前移**——它含管理员用户名，整体前移等于把同一个 bug 搬到管理员校验上。

### 3. 判读教训：`99999` 不能作判据

端口校验这一侧有一条判读教训，和第五章那条假零命中同类：

**既有规则只校验「是数字且 > 0」**（已对照旧版代码确认）。所以 `99999` 被放行是**正确行为**。但问题在于：**校验读默认值 5432 时它会过、读真实输入时它也会过——两种情况表现完全一样。**

**只有非数字输入能把二者分开。** 这正是这个 bug 当初能潜伏下来的原因：用合法值测，坏的和好的看起来一模一样。

### 4. 副产物：三条分支里两条是死代码

收口时顺带查证出：原计划做的两个对照组**走不到**。两条硬证据：

1. **整个安装器没有任何 feature / bundle 勾选面板**——全文只有 5 个 bundle、3 个 install set 的**定义**，**零个 chooser action** → 用户无法「只勾数据库、不勾 Core」；
2. **「安装类型」面板排在数据库配置组之后**，且在那之前全文没有任何地方给特性列表变量赋值 → 判定时它恒为默认值（同时含两个组件）。

所以「Typical / Custom」是 **install set 级**选择、生效时点在数据库配置之后，**不是「自定义装哪些功能」**。四轮实测无一例外落在同一个分支，面板顺序也印证了这一点。

**方法论留档**：IA 里判断某个文件归属哪个 feature，**看 `InstallComponent` 的 `refID` 引用，不是看定义位置的行号**。有个文件的定义就落在数据库 bundle 的行号区间内，但只被 Core 引用，归属是 Core。

顺带暴露一个**当前不触发的跨 feature 依赖**：服务注册归 Core，而 `net start` 却硬编码在数据库那条复合命令末尾并以 `&` 连接、规则表达式为空 → 将来若真开放单装数据库，会去启动一个没注册的服务。已登记，以免将来误判成本轮引入。

> **教训（两条）**：
> ① **把一个校验动作前移时，必须先查清它读的变量由谁在何时赋值。** 「面板变量 → 归一化变量 → 校验」是三段式，**只挪中间一段必坏**，而且可能坏向两个相反的方向。
> ② **用合法值做测试，分不开「读对了」和「读错但恰好也过」。** 设计判据时要专门找一个「两种情况会给出不同结果」的输入——本例是非数字端口，第一章是 `apt-mark` 标记，第五章是日志条目计数。

细节见 **`os-support/07` T-11 / T-16**（内部真源，不随本目录）。

## 八、 判据纪律：哪些证据会骗人

> 本章是这六周里最可迁移的产出。它不讲某个缺陷怎么修，讲**哪些看起来像证据的东西其实证明不了任何事**。每一条都是实际吃过亏之后写下来的。

**零命中。** 拿英文关键词去搜中文日志，得到零命中并据此断言「这个动作从未执行」。**零命中是最容易造假的一类证据**——拼写、语言、大小写、时间窗口、日志轮转，任何一个偏差都会产出它，而它看起来像铁证。做零命中判定前，先用一个**已知一定存在**的字符串验证搜索方式本身是对的。

**`[WARN]`。** 「这两条 WARN 可以忽略」——依据是「功能验证通过了」。但功能验证**只证明了那一台机**，而那两条 WARN 恰恰是一个真实缺陷的唯一征兆。**`[WARN]` 能不能忽略，不能用「功能验证通过」来判。**

**diff 规模。** git 报 1566 行删除，看起来是一次大改。按行做多重集比对，**真正消失的只有 6 行**，其余全是移位。反过来也成立：另一轮 git 报上千行变更，按 XML 节点比「自身属性」，**真正改动的只有 12 个节点**（有差异的 152 个里 139 个只是容器）。**行数与真实改动量无关。**

**合法值测试。** 端口填 `99999`：校验读默认值时过、读真实输入时也过，**两种情况表现完全一样**。只有非数字能分开。同理，版本号区分不了「跳过安装」与「装了同一个版本」，只有包管理器的 manual/auto 标记能分开。

**「装完能用」。** 用它证明「数据被保留了」是错的——**库被重建之后同样能用**。硬判据是文件时间戳。同样，「系统起来了」证明不了「配置值是对的」，因为多数配置错误会退化成一个可用但语义不同的值。

**「文件存在」。** 用「暂存文件在那儿」证明 ACL 加固生效是错的——那段代码用的是静默执行封装，**吞掉一切失败**。唯一算数的证据是**直接查 ACL**：非提权 shell 连读取权限都被拒，才证明断继承生效了。

**不区分情况的日志行。** 动作打印的「已写入转义后的值」这句话**不区分中英文**——同一天用纯 ASCII 名字的三轮也逐轮打出该行。它只证明动作找到了文件。**用一条在成功和失败时都会出现的日志当判据，等于没有判据。**

**归一化之后的打印值。** 脚本打印的是**归一化之后**的参数值，而「正确传参得 0」「没展开传字面量被归一成 0」「展开成空串被默认值兜底成 0」**三者现象完全相同**。只有传另一个值（非默认值）才能把它们分开。

**静态检查全过。** 一次改动的四条静态自检（ID 唯一性、XML 良构、定义链未变、引用总数 delta 为 0）全部通过，而那个动作**根本没有被调度**。静态检查覆盖不了执行引擎的调度语义。

> **教训**：上面九条有一个共同结构——**「在好与坏两种情况下都会出现的观察，不是判据」**。设计验证时该问的不是「怎么证明它对了」，而是「**如果它错了，我看到的会有什么不同**」。如果答案是「没有不同」，那这个观察就该丢掉，换一个。

## 九、 证伪与自我订正：论据倒了，做法保留

这六周里**主动推翻了自己的多条结论**。记在这里不是为了展示过程，而是因为**推翻之后怎么处理**才是方法。

**glibc rebase 是 Red Hat 的文档笔误。** 「RHEL 9 小版本间 glibc 从 2.34 rebase 到 2.39」曾是「免全量回归」最硬的依据。实测推翻：该版本 release notes 里那个数字与同一节的其它工具链版本互相矛盾（那些都是旧版的值），而 2.39 是**下一个大版本**的数；实机 `ldd --version` 给的是 2.34，内核版本与该版本自述精确吻合。

**OpenSSL 硬边界站不住。** 三个版本的 `postgres` 都只要 `OPENSSL_3.0.0`，而该大版本内部从 3.2.2 到 3.5 全是同一个 soname、都提供该符号。

**CWE 定性与工单标签不一致。** 三条被标为「命令注入」的告警，实际都走 `ProcessBuilder(List)`、**不经 shell**，命令注入不成立；真正的弱点是**不可信搜索路径**（环境变量派生值落在 `argv[0]`，能决定执行哪个二进制）。而那个 `critical` 标签是工单系统**按 CWE 命中某个 Top 25 清单自动抬**的，扫描器自身给的是 Low。**判处置时不能被标签带走。**

**同类问题不能套用上次的答案。** 两次依赖覆盖，机制正好相反：一次是**上游 BOM 不托管那个坐标、没有 property 可用**，只能在 `dependencyManagement` 里显式钉；另一次是**有 property 但管不着**——它钉在第三方的父 POM 里，而属性是在**声明它的 POM 上下文**里求值的。把上一次的做法当通用答案会直接走错。

**Ubuntu 的历史结论在「离线」这个维度上全部不成立。** 发现那台「通过」的机器是联网救的之后，把支持矩阵里 Ubuntu 两行**撤绿**，带包后当日**断网重测**才转绿。并定下规矩：后续 Ubuntu 回归**一律断网做，且把网络不可达的输出落进结果文件**——那是区分「通过」与「联网假象」的唯一凭据。

> **教训（两条）**：
> ① **论据倒掉时，先分清倒的是论证还是做法。** 两条承重论据全没了，但「按小版本分包、包标签校验、逐版本实测」三项做法一项没改，只是理由换成了「宿主机状态差异」。如果当时连做法一起改，就会因为一个文档笔误丢掉正确的策略。
> ② **撤销一个自己已经宣布通过的结论是有成本的，但那个成本远低于让它留在矩阵里。** 支持矩阵是对外声明的依据，一行假绿比一行空白危险得多。

## 十、 单变量对照实验的设计

这六周里几个关键结论都不是「测一遍通过就收工」，而是配了一组**只差一个变量**的实验。设计要点记在这里。

**只动一个变量，其余原样。** 在失败机上**只**手工装上缺失的库，包与流程全部原样重装。四条指标同向翻转（判读 MISSING→OK、`ldd -r` not found→已解析、验证集 4/11 FAIL→8/8 PASS、日志 WARN 8→0），并且两轮残留检查全部为空，排除「靠上一轮残留蒙过」。

**留一台从未被人工干预的机器。** 这是最容易省掉、也最不该省的一步。**手工补过的机器无法区分「代码生效」与「残留生效」**，所以另一台失败机被刻意保留不动，等代码合入后用新包验证——这一步证明的是代码在起作用。

**找一组只差目标变量的现成环境。** 两台同版本 Ubuntu，起点相同、**只差网络**。它们的安装日志差别只有一行，而结论是「安装器有一条隐式联网依赖」——这个结论在任何单台机器上都得不出来。

**主动去验相反的那条分支。** 一台自带该库的机器验的是「探测到已有就跳过」，与另一台的「探测不到就装」是相反路径。**同一份代码在两台机走了相反分支**，「见包就装」这个假设由此证伪。只验一侧拿不到这个结论。

**判据要选能把两种情况分开的那一个。** 上一条里，版本号**区分不了**「跳过」和「装了同一版」——因为发过去的就是同版。能分开的是包管理器的 manual/auto 标记：`dpkg -i` 一旦跑过，标记必然翻转。

**给结论找互不相关的第二条证据链。** 选包结论是从官方门户的频道信息读出来的，而社区重建版各小版本 vault 里的实际版本分布**独立地**给出了同一个结果。两条不相关的证据链指向同一结论，比一条强得多。

> **教训**：实验设计的核心问题不是「怎么验证它对」，而是「**这个观测能不能把两种可能分开**」。前一节九条判据陷阱，本质上全是这个问题的反例。

## 十一、 IA 工程纪律（本轮新增）

以下七条都是这六周里实际踩出来的，可直接作为动手前的检查项。前两条与 IA 无关，任何框架都适用。

1. **`substitute()` 只用于自己写的模板串；凡是读用户输入，一律用 `getVariable()`。** 模板展开接口会对展开结果继续解析。
2. **custom code 碰框架铺下来的文件，要向框架「问」路径，不要按自己熟悉的平台「拼」路径**；越界检查的锚点要跟着实际落点走，而不是锚在安装根。
3. **locale 条目按 objectID 绑定。** Designer 复制或新建的节点拿到新 ID，两个 locale 文件里的命中数就是 0，运行时静默回退到英文。**凡在 Designer 里新增/复制带用户可见文案的节点，都要顺手查一遍它在 locale 文件里的命中数。**
4. **凡进过 Designer 的轮次，都要重跑逐节点比对，重点看「删除 = 0」。** Designer 保存会剪掉「只有打包归属、执行树零引用」的节点。比对要按 XML 解析比**自身属性**（嵌套子对象只记 ID，避免容器误报）；导出基线必须按字节导（用 shell 重定向，某些 PowerShell 写文件方式会弄坏中文节点，而 cmd 里 `^` 是转义符会吃掉 revision 后缀）。
5. **`uniqueObjects` 必须与 objectID 总数相等。** 手工改完 XML 要同步这个计数（曾出现工具写 1276、实际 1278）。
6. **让一个「一直为假」的条件变成可以为真时，把依赖它的所有节点列一遍。** 新增逻辑有人审，被顺带唤醒的旧逻辑没有。
7. **Debian 系与 RHEL 删数据库集群的手法相反**：Debian 必须用 `pg_dropcluster`（裸 `rm` 数据目录会留下注册信息，制造「注册在、数据不在」的半态）；RHEL 无注册机制，裸删才是对的。**别把一边的习惯带到另一边。**

另记一条构建期陷阱：跑 `mvn` 会把源码树里的 `application.properties` 写成占位符形式（资源过滤污染源码树），提交前记得还原。

## 十二、 决策留痕：不做、暂缓、技术债是三类

结项时的开放项被分成**三类而不是两类**，并且每一类都写了依据。这个分法本身值得留档。

- **已决不做**：权衡后放弃，**写明代价**。例如放弃给两个版本补脚本取证，代价是「这两个版本至今没有完整库基线」——这句话被写进结果目录 README 的开头，**防止后人从「目录里没有文件」误推「没验过」**。
- **暂缓**：只是排在后面，不是否决。「暂缓 ≠ 已决不做」被显式写出来，因为这两者在清单上看起来一样，但处置成本差一个数量级（一项随时能动手，逐行位置都查好了；另一项要改安装器的失败语义、回归范围可能超出改动本身）。
- **保留现状 / 技术债**：明确承认「根因大概率成立，但修复方案的回归面超过收益」。例如某个运行期状态机缺陷，补偿式修复要新增机制、架构式修复要动更新钩子加锁并引起大规模回归，叠加触发概率低 → 留作技术债。

另有一类**只登记不立项**：例如卸载正则漏删两个包。不立项的理由很具体——**其中一个是常用库，正则一加就变成无条件删，得先查清还有谁依赖它**（单机观察反向依赖为空，不足以推广）。

> **教训**：**「不做」比「做」更需要写依据。** 做过的事有代码和日志作证，不做的事只留下一个空白——而空白会被后人读成「忘了」或「没想到」。三分类 + 写明代价，是让这个空白变成可审计的决定。

## 十三、 方法论边界：这套论证覆盖不到什么

最后单列这一节，因为它是引用本文任何结论的前提。

**支持范围的论证是割集论证**：PI 的代码是同一份 → 跨版本差异只能来自 OS → 穷举 OS 依赖面即可覆盖。它有四个已知漏洞：

- **穷举完备性是假设**，不是证明；
- **「应用层与 OS 解耦」只是近似**，locale 与排序、文件系统语义、子进程行为等至少六类实则吃 OS；
- **最小验证集只测「能装能起」，不测「行为正确」**；
- **对非 OS 依赖完全沉默**——这一条已被具体案例坐实：一个硬件类插件因服务降权而失效，属运行期功能回归，与安装成功无关，安装类测试完全抓不到。

**缺陷收口这条线也有一个整体盲区**：所有验证都是全新安装 / 卸载 / 重装，**升级路径不在范围内**。挂起的几项恰好都在这条路径上（旧版升级待验证、备份恢复模块待重写、若干校验组在升级时跳过、手工补的升级门控无独立验证点）。**这不是零散技术债，是同一条路径上的一簇**——真做升级版本时会一起暴露。

> **教训**：**论证的价值一半在结论，一半在边界。** 一个写明「我覆盖不到什么」的结论可以被安全地引用；一个没写边界的结论会被引用到它根本不成立的地方去。
