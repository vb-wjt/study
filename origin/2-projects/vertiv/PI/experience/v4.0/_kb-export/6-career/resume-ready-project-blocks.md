# 可直接粘贴的项目经历块（按岗位三个版本）

> **怎么用**：确定投什么岗位 → 取对应版本 → 整块粘贴 → 按目标 JD 微调技术栈行。三个版本讲的是**同一段经历**，差别在于**取哪些事、用什么语言讲**。
> **为什么要分版本**：这段经历的价值不会自动兑现，它取决于岗位类型。拿平台/交付工程的经历去投通用业务后端，双方都会觉得不匹配——不是经历不够，是没翻译。
> **配套**：面试深挖的问答见 [`portfolio-and-mock-interviews.md`](portfolio-and-mock-interviews.md)（含 17 道模拟题与术语翻译层）。数字的口径与出处见本文末尾「可量化事实清单」，**每个数字都要能当场解释怎么来的**。

> ⚠️ **三条使用纪律**
> 1. **数字只用清单里有口径的**。简历上的数字会被追问「这个 100% 是怎么统计的」，答不上来比不写更糟。
> 2. **动词用可核验的**（定位 / 设计 / 实现 / 验证 / 提出并说服），不用「主导 / 推行 / 负责整体」。四年多经验说「主导」，面试官追一句汇报关系就露，而且会连带折损真实的部分。
> 3. **不写公司名与产品名**，用类别描述。下文已按此处理。

## 版本一 · 通用 Java 后端

> **适用**：业务后端、中间件、基础架构、安全开发、Agent / 探针开发、部署工具链。
> **取舍逻辑**：弱化打包工具本身（那是不可迁移的领域知识），突出**基础设施 Java、诊断深度、以及三个可讲成系统设计的题材**。这一版翻译量最大，但也是覆盖岗位数量最多的一版。

**企业级基础设施监控系统 · 安装部署与交付工程**　`2026.05 – 2026.09`

负责该产品安装部署链路的技术改造与交付验证。周期约四个半月，跨 Windows / RHEL / Ubuntu 三个平台、四个代码仓库；产出覆盖数据底座替换、伴生引擎替换、安全合规整改、操作系统支持范围论证与发布前缺陷收口五个阶段。

- **数据底座与伴生引擎替换**：在一个基于闭源打包工具、约四万行声明式配置的遗留安装系统上，把数据库从 MongoDB 替换为 PostgreSQL 18，把旧版 C++ 采集引擎替换为 Java 21 实现的新引擎，**服务数量从 5 个收敛为 1 个**；重写服务生命周期契约（注册 / 启动 / 卸载三段）与双用户权限隔离。服务化机制**先定位到主服务已有的 wrapper 并复用**，而非另造一套，以此压低回归面。
- **配置加载与编码链缺陷定位（Spring Boot）**：定位到一条**静默**缺陷——打包器把用户输入以裸 UTF-8 写入 `.properties`，而 Spring Boot 读 `.properties` 固定用 ISO-8859-1，导致中文管理员账号落库为含不可打印控制字符的串、**账号物理上无法登录，且安装全程零报错**。通过字节形态比对将范围收敛到业务逻辑之前（排除 GBK 等竞争假设），并**反编译 `OriginTrackedPropertiesLoader` 确认框架侧的转义与反转义构成恒等变换**——证明「模板内转义」这条路是原理性死路。最终方案为落盘后由自定义动作按 ISO-8859-1 字节透明改写目标行，配 7 例单测；两平台实测以字节计数（非 ASCII 字节为 0、反斜杠计数与大小写形态）作为判据。
- **用户输入被模板展开吞噬（截断与注入）**：定位到框架的字符串替换接口会把**第 1 与第 2 个 `$` 无条件配对**当作变量引用，导致 32 字符输入落盘为 19 字符；**逐字节验证删除区间与实测值完全相等，并算出竞争假设（按 `%` 配对）的结果不符以排除之**。进一步确认危害不止截断——两个 `$` 之间若为真实变量名则替换为该变量的值，**性质上是变量注入**。修法是区分「对象通道」与「字符串通道」两类 API，把三处读用户输入的调用改为对象通道；并反编译定位到框架侧单点（`passByValue` 为真时对未知 token 的处理分支），确认可通过配置开关闭合而无需改代码。
- **共享状态生命周期边界的设计缺陷**：系统存在结构性不对称——数据库走固定路径的系统集群，而证书 / 系统目录 / 伴生引擎暂存库跟随用户选定的数据目录，**一半固定、一半跟随**。在「数据目录变更而集群仍在」时两者脱节，症状为**可登录、通讯正常、设备列表齐全，但无任何数据被采集**（唯一判据是引擎日志的一行计数为 0）。修法为将暂存库迁至与密钥库平级的固定路径（但不并入密钥库——两者备份与清理策略不同），并补「无集群守卫」与「旧位置回退」两个守卫。
- **密钥体系与运行权限最小化**：实现免 KMS 的每实例唯一密钥体系——安装期生成随机 nonce，以 **HKDF-SHA256** 按用途分域派生 AES-256-GCM 子密钥，根治「一次编译、全网同钥」；用 RFC 5869 官方测试向量 + 跨实现 parity 向量钉死两侧实现字节级一致。灾备方案上**拒绝引入主密钥兜底**（那会重建单点），改为「密钥随数据一起备份」。同期完成三服务运行权限降级与文件 ACL 收敛，并建立脚本化门禁（两平台分别 53/0、35/0）+ 多机矩阵实机验证。
- **静默失败的工程治理**：针对批处理脚本中因 CMD 预解析机制导致的递归删除事故（曾删除开发机系统盘内容），重构脚本消除对复合块内动态变量的依赖，并编写静态审计脚本合入 CI 作为强制门禁，**对已知的若干类危险删除写法做 100% 拦截**（静态检查无法覆盖运行期拼接，该边界已写入文档）。

**技术栈**：Java 21 / Spring Boot / JCE（HKDF、AES-GCM、keytool、PKCS#12）/ PostgreSQL 18 / Maven / Ant / GitLab CI / Bash / PowerShell / systemd / Windows 服务与 ACL / SQLite

## 版本二 · 平台工程与交付工程

> **适用**：平台工程、基础设施、私有化部署 / 信创交付、发布工程、SRE、DevOps。
> **取舍逻辑**：这一版**几乎不用翻译**——经历原样就是岗位内容。突出依赖契约、离线确定性、跨平台一致性、可复跑验证。

**企业级基础设施监控系统 · 跨平台与离线交付**　`2026.05 – 2026.09`

负责将该产品的安装部署链路从单 Windows 扩展到 RHEL / Ubuntu，并把「支持哪些操作系统版本」从经验判断升级为可论证、可复跑的结论。周期约四个半月，覆盖 **9 个受支持发行版版本**，全部要求**离线（无外网）确定性安装**。

- **把隐式 OS 依赖显式化为契约面**：将系统按「应用层 / 数据库原生层 / OS 集成层」三层分解，判定只有数据库原生层随小版本变（上游按小版本分包；应用层因自带 JRE、不读系统加密策略而与 OS 基本解耦）。把安装器对操作系统的依赖显式化成 **16 项契约面**并逐项标注版本敏感性，据此定出支持矩阵与测试分工（每大版本一个全量基线 + 其余小版本跑 **11 项最小验证集**）。**并明写论证边界**——这是割集论证不是全集，四个已知漏洞逐条登记，其中「对非 OS 依赖沉默」后被一个硬件类插件的运行期回归坐实。
- **定位一条未被分发的离线硬依赖，两次发作均闭环**：数据库新版本引入 `io_uring` 并硬链 `liburing.so.2`，而该库在目标发行版属非基础仓库、离线包未携带，叠加安装脚本的 `--force --nodeps` **关掉了本可干净拦住它的依赖检查** → 包照装成功、初始化一跑就炸、**界面照报成功**。定性为**宿主机状态差异而非 OS 版本差异**（此前通过的机器只是恰好预装该库），并据此把「逐版本实测」的依据从「ABI 边界」换成「宿主机状态差异」。修复覆盖范围**刻意不均匀并写明理由**：一个大版本探测 + 带包、另一个只探测并明确报错、还有一个免检（包属性决定）。
- **发现并撤销一个假通过的验收结论**：查实此前记为通过的一台机器是被脚本内一句注释写着 best-effort 的联网补包命令救活的——三条独立证据（包管理器历史记录、包文件 mtime 比装机日晚七个月、反向依赖唯一指向数据库包），而**两份安装日志的差别只有一行**。据此判定该发行版全部历史结论在「离线」维度上不成立，**撤销矩阵通过标记并断网重测**，并定下「后续回归一律断网、且把网络不可达输出落进结果文件」的规程。
- **用单变量对照实验替代一次性验证**：在失败机上**只**补装缺失库、其余原样重装，四项指标同向翻转（判读 MISSING→OK、`ldd -r` not found→已解析、验证集 4/11 FAIL→8/8 PASS、日志 WARN 8→0）；**刻意保留另一台失败机不做人工干预**作为干净验证机，因为手工补过的机器无法区分「代码生效」与「残留生效」。同一份代码在两台机走**相反分支**（探测到已有则跳过 vs 未探测到则安装），由此证伪「见包就装」；该轮的关键判据选包管理器的 manual/auto 标记而非版本号——**因为下发版本与宿主同版，版本号区分不了这两种情况**。
- **把验证做成可复跑资产**：编写两个环境指纹采集脚本（装前体检 + 装后取证，共 **1,737 行**），内置 9 版本 × 8 组件预期值表与**五档判读**（后增第六档「下界比对」以处理同一 LTS 内向前滚动的内核与仓库版本，比较改用版本号排序而非数值排序）。迭代中修掉 **10 个会造成误判的真 bug**，其中 4 个足以让一轮验证结论作废：日志 glob 匹配到无关文件并据此判 PASS；伞单元「按设计就是 exited」使该检查项形同虚设；薄别名服务被按真服务判而稳定误报；强制访问控制检测在另一发行版上会误报为偏离基线。
- **离线交付的合规判断**：识别出**再分发某商业发行版的构建产物属合同与商标问题，与开源许可证是两件独立的事**；解法是改取同一源码包的社区重建版构建，并逐项核对 Provides / Requires 与原构建一致。同时定下「按符号验而非按版本号验」的入库规则（某构建装得上、`ldconfig` 有输出，**就是缺目标符号**），并把「带包」与「探测」拆开实现，使合规风险不阻塞工程进度。
- **跨平台一致性与卸载架构**：定位并重写两道隐藏的发行版专属早期门禁（OS 白名单原先靠「版本号含 7」的**巧合子串**放行、依赖预检硬绑单一包管理器）；用启动器 dump **证伪**「运行时不兼容」的直觉判断后，把 Linux 卸载脱钩为单一事实源脚本（并复用于安装失败回滚），实现零残留卸载且 **Windows 链零回归**（全部平台动作以共享规则门控、零新增对象 ID）。

**技术栈**：Bash / systemd / RPM 与 dpkg / PGDG 离线包治理 / glibc 与 soname 符号版本 / SELinux 与 AppArmor / PostgreSQL 18 集群管理（`pg_createcluster` / `pg_dropcluster` / `initdb`）/ Maven / Ant / GitLab CI / PowerShell / InstallAnywhere

## 版本三 · 安全工程

> **适用**：应用安全（AppSec）、安全开发、安全合规、密码学工程、私有化交付安全。
> **取舍逻辑**：突出密钥生命周期、权限模型、漏洞可利用性分析，以及**「论证清楚后坚决不做」的克制**——后者是区分执行者与决策者的地方。

**企业级基础设施监控系统 · 安全合规整改**　`2026.07 – 2026.09`

负责该产品安装部署链路的安全合规整改，围绕上游 7 个安全条目收敛三类问题：明文与硬编码凭据、TLS 证书不唯一、服务运行权限过高。硬约束是**离线 / 私有化部署，不能引入第三方 KMS**，且不能破坏既有安装链与跨平台兼容。

- **免 KMS 的每实例唯一密钥体系**：根治「对称密钥被编译进产物、一次编译全网同钥」（该类问题 CVSS 高危）——安装期生成随机 nonce，以 **HKDF-SHA256** 按用途枚举分域（通用 / 数据库 / TLS / SNMP）派生 **AES-256-GCM** 子密钥，使同一份密文换机即不可解；**密文格式不变**以保证存量解密零改造，并强制显式域标签（裸标签直接抛异常，杜绝「忘记指定域而悄悄用了默认钥」）。用 **RFC 5869 官方测试向量 + 跨实现 parity 向量**钉死主系统与伴生引擎两侧派生结果字节级一致，并做负向测试确认失败时在启动最早期 fail-fast 且**报错点名文件与后果**。
- **密钥灾备的取舍**：机器绑定的代价是 nonce 丢失即历史密文不可解。**明确拒绝「存一把主密钥兜底」**——那等于重建一个全网单点，回到被修的老问题。最终方案是「卸载即删 nonce，灾备靠备份数据时一并备份 nonce」，使密钥与其保护的数据同生共死、同备份同恢复：既不新增单点，又可恢复。
- **大对象加密的信封方案**：备份归档原用一把硬编码 AES 密钥（一处泄露则所有客户归档可解）。方案选型的**决定性依据是错配而非偏好**——通用密钥服务是为属性与短文本设计的字符串级密码器，拿它加密数百 MB 归档流不合身；改为每次备份用 `SecureRandom` 现生数据密钥做流式 AES-256-GCM，仅把数据密钥用主钥封装写进归档头（一档一钥 + 每机唯一）。同时**明示代价并写入运维预期**：归档只能在原机恢复，跨机需走「nonce 随数据备份」的灾备链。
- **每实例唯一 TLS 证书与信任链克制**：安装期为两个服务各生成唯一自签证书（RSA-3072 / SHA256withRSA），根治「全网相同证书指纹」，重装换指纹、卸载清除。并**追查真实信任链**发现某导入步骤在 trust-all 主通道下实为 no-op，判定「克制不做」，避免无效加固。
- **服务运行权限最小化与 Windows 深水区**：三服务从最高权限降至最小权限。**选型经过一次返工并因此拿到关键洞察**：首版选虚拟服务账户作登录身份（天然一服务一 SID、免密码），但在域信任断开的机器上直接报错 1057，而客户现场的域状态不可控；改为内建的 `LocalService` 作登录身份、再用服务 SID 类型设置让令牌携带唯一的服务 SID——**登录账户与授权主体可以解耦**，授权隔离一点没丢（一个服务碰不到另一个服务的数据目录），却绕开了域依赖。攻克 `initdb` 受限令牌撞 ACL、默认路径继承只读 ACL 等深水坑。
- **最小权限的落地准则**：**代码归特权属主、运行账户只读；只有数据目录对服务账户可写**——即便运行进程被攻破也改不动自己的代码，直接封死「篡改二进制 / 写入持久化后门」这条攻击链。落地前**先枚举所有运行期写入路径**确认无冲突（若存在自更新需求，正解是分离可写暂存区与只读代码区、由特权更新器落盘，而非开放代码目录）。
- **加固生效的可证明性**：把合规验收从「肉眼核对」升级为「一键复现」——脚本化门禁（两平台 53/0、35/0）+ 三机 / 四机 / 双发行版多机矩阵实机验证。**并明确区分「命令跑过」与「限制生效」**：ACL 断继承的判据是非提权 shell 连读取该目录 ACL 都被拒绝，而「暂存文件存在」什么都证明不了（相关代码使用静默执行封装、会吞掉一切失败）。
- **SAST 工单的重新定性与克制**：完成路径穿越等条目的修复后，对若干高危标签工单做可利用性分析并**给出与标签不同的定性**：三条被标为命令注入的告警实际都走进程构建器的列表形式、**不经 shell**，命令注入不成立，真实弱点是不可信搜索路径；而该 `critical` 标签是工单系统按 CWE 命中某清单**自动抬级**的，扫描器自身给的是低危。另有若干条属**坐标级为真、利用面为零**（依赖物理进入产物但调用面不激活），逐条给出证据级结论而非一律修。同期以**威胁模型 + 爆炸半径**论证「该不做的坚决不做」（某专用密钥的安全增益≈0 而改造有回归风险；静默安装移除；空默认口令抢注窗口的残余风险取舍）。

**技术栈**：Java 21 / JCE（HKDF-SHA256、AES-256-GCM、PBKDF2 对比、keytool、PKCS#12 / JKS）/ Spring Boot 配置加密 / Windows 服务账户与令牌模型（per-service SID、`sc sidtype`、`icacls` 继承与属主）/ Linux 权限（专用服务账户、`sudoers` 白名单、`CAP_NET_BIND_SERVICE`）/ TLS 1.3 / Snyk / PowerShell / Bash

## 可量化事实清单（三版复用，每项含口径）

> **用法**：简历 bullet 里的数字只从这里取。每一条都标了口径与出处，**面试被追问时要能当场解释怎么统计的**。

**周期与范围**
