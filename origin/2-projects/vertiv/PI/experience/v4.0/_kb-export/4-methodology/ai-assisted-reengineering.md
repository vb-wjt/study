# 小众与遗留系统下的 AI 协同与重构方法论

> **最后更新**：2026-08-14（新增方法论五/六与实战案例五/六，均由安全整改催生；原迁移/重构方法论保持不变。配套硬核复盘见 [`06-security-hardening-postmortems.md`](../3-postmortems/security-hardening.md)）
> **文档用途**：总结在面对缺乏公开训练数据、闭源且充满黑盒行为的遗留技术栈（如 InstallAnywhere）时，如何摆脱传统的“AI 代码外包”模式，升维建立“证据驱动、安全沙箱、上下文对齐、证伪式假设检验”的现代 AI 协同重构方法论，并提供四大经典实战案例（GnuWin32 unzip.exe 静默崩溃排查、ZE 服务链 build-5 至 build-11 执行断层逆向推导，以及 Linux 双平台的 IA `$…$` 内联脚本吞噬定位、卸载器 exit 218 黑盒脱钩），为团队提供在复杂工程中高效驾驭 AI 的实战指南。配套 Linux 交付/复盘见 [`05-linux-delivery-and-qa-guide.md`](../5-delivery/linux-delivery-and-qa.md) 与 [`02-hardcore-technical-postmortems.md`](../3-postmortems/migration-and-platform.md) 第六章。

## 一、 遗留与小众技术栈的 AI 协同痛点

在面对 React、Spring Boot 或 Python 等主流技术栈时，AI（如 ChatGPT、Claude、Gemini）表现得极其出色，因为互联网上有海量的公开代码、博客和 StackOverflow 问答。

然而，在面对**遗留、闭源或极其小众的技术栈**（如 InstallAnywhere、Java Service Launcher、过时的 CMD 批处理机制）时，团队会遭遇以下三大 AI 协同痛点：

1.  **海量知识盲区与严重幻觉**：AI 的训练数据中几乎没有 InstallAnywhere 2025 的内部 XML 结构定义。当被要求“在 XML 中添加一个新服务”时，AI 会根据常识编造出看似合理但编译器根本不识别的 XML 节点，导致频繁的构建失败。
2.  **黑盒行为难以预测**：像 IA 编译器在构建时静默剥离新增 ObjectID、或者 inline keyFile 在 fileSize=-1 时触发 C++ 堆损坏等底层 Bug，AI 根本无法通过静态代码分析预知。
3.  **安全隐患被放大**：AI 在编写 Windows CMD 批处理脚本时，极易忽略“延迟展开”等底层机制，生成带有严重安全隐患的代码（如未受保护的 `rmdir /s /q`），在拥有管理员权限的安装器中运行会造成灾难性后果。

## 二、 AI 协同模式的升维转变：从“代码外包”到“推理伙伴”

为了在本次重构中突破上述痛点，我们彻底改变了与 AI 的协同模式，总结出以下三大核心方法论。

### 方法论一：从“任务外包”转向“证据驱动的推理伙伴”

*   **传统错误模式（代码外包）**：直接向 AI 发送指令：“帮我写一个在安装器中解压 zip 并启动服务的 XML 片段。”
    *   *后果*：AI 产生严重幻觉，生成一堆无法通过编译的垃圾 XML。
*   **现代升维模式（证据驱动）**：将 AI 定位为**“拥有严谨逻辑的推理伙伴”**。
    1.  **提供 baseline 证据**：将现有的、已被编译器验证通过的正常 XML 节点（如 `THIRD-PARTY-NOTICES.gotools` 节点）作为“铁证”提供给 AI。
    2.  **提供报错日志**：将 GitLab 构建失败的日志（如 Heap Corruption 退出码 `0xC0000374`）完整提供给 AI。
    3.  **引导逻辑推导**：不让 AI 瞎猜，而是引导其进行差异对比（Diff Analysis）：“对比 build-38（成功）和 build-39（失败）的日志，分析为什么相同的代码在 shutdown 阶段会触发 JVM 崩溃？”
    4.  **推导黑盒规律**：AI 通过分析崩溃栈，精准推导出“C++ 编译器在回写 fileSize 时发生越界写入”这一底层规律，从而指导我们设计出“劫持已有正常节点”的破局方案。

---

### 方法论二：建立“静态验证与安全沙箱”过滤机制

AI 生成的代码（尤其是涉及系统级删除、注册表修改的脚本）绝对不能直接运行。必须在 AI 与真实系统之间建立一层**“安全隔离沙箱”**。

```
+------------------+         +--------------------------+         +------------------+
|  AI 生成的脚本   | ------> |  静态安全审计沙箱        | ------> |  真实系统执行    |
|  (可能含高危命令) |         |  (verify-destructive)    |         |  (100% 安全闭环) |
+------------------+         +--------------------------+         +------------------+
                                          |
                                          | (审计未通过：拦截并打回)
                                          v
                                 [ 自动反馈给 AI 修复 ]
```

1.  **编写静态审计工具**：在重构初期，率先编写如 `verify-destructive-commands.ps1` 这样的静态审计脚本。
2.  **自动门禁拦截**：将审计脚本合入本地开发流程或 CI 门禁。
3.  **闭环修复**：一旦 AI 生成的代码包含未受保护的 `rmdir`，审计工具立即拦截，并将报错信息作为上下文再次输入给 AI，促使其生成防御性极强的修复代码。
4.  **工具优于人脑**：不依赖人工 review 来保证安全，而是用工具和规则强制约束 AI 的产出。

### 方法论三：上下文快照策略 (Context Snapshot)

在跨越数天、涉及多技术栈（Java、XML、CMD、PowerShell、Maven）的复杂重构中，AI 极易因为对话轮次过多而发生“遗忘”或“上下文漂移”。

我们实施了 **Context Snapshot（上下文快照）** 机制：

1.  **建立单一事实源**：在项目根目录下维护 `docs/context-snapshot.md` 文件。
2.  **动态 checkpoint**：每当攻坚取得阶段性突破（如 Windows 装机验证通过、解决 Heap Corruption），立即更新快照中的“关键研究结论”和“关键代码位置”。
3.  **新对话无缝恢复**：在开启新的 AI 对话或切换工具时，第一步指示 AI 静默读取该快照。
4.  **消除认知偏差**：确保 AI 始终掌握最新的工程状态、路径映射和技术决策，避免其给出与历史决策冲突的过时建议。

---

### 方法论四：证伪式假设检验与静态验证的边界认知（Linux 双平台催生）

在把只在 Windows 验证过的安装器扩展到 **RHEL + Ubuntu 双平台**时，我们踩到两类新陷阱：一是**顺着直觉的假设猛冲**（“卸载器 `exit 218` 一定是 Java 21 不兼容”），二是**过度信任静态检查**（“`bash -n` 过了就一定能跑”）。为此在原有三条方法论之上，补充两条：

1.  **证伪优先于投入**：任何跨平台失败假设，先用证据**证伪**再动手，避免朝错误方向投入人力。
    *   *范例*：用 IA 安装器的 `lax_dump` 证明它在 Zulu 21 上能**完整跑完** → 一举推翻“Java 21 不兼容”的直觉误判，把排查火力从“升级/降级 JVM”收敛到“卸载器 native 启动器的 JVM 引导”这一真问题。
2.  **认清静态验证的边界**：`bash -n`、判定矩阵只覆盖 shell 语法与逻辑，**不覆盖** InstallAnywhere 打包时的 `$…$` 变量替换层，也**不覆盖**离线依赖链的完整性。凡涉及 IA 变量替换、离线包、发行版差异的改动，**静态全绿只是必要条件，实机验证才是充分条件**。

> 教训一句话：**别让 AI（和自己）把「直觉假设」当结论、把「静态通过」当交付**——跨平台扩展尤其如此。

---

### 方法论五：合规工程化——把“验收”变成“可复现门禁”（安全整改催生）

安全整改（SECURE/SEC-REQ）与功能重构最大的不同，是它有**外部合规验收**：不是“装上了就行”，而是“**每一条安全属性都要可证明、可复现**”。为此把方法论二的“静态安全沙箱”规模化为一套**四文档 + 门禁脚本**的工程：

1.  **单一真源的文档链**：`00-总览`（issue 关系）→ `01-台账`（问题/证据/验收，两类视角）→ **`02-路线图`（进度唯一真源，状态只在此维护）** → `qa-impact`（QA 影响面与回归）。这是方法论三“上下文快照”的升级——**快照（`context-snapshot.md`）只作入口索引、指向真源，安全进度的唯一真源是路线图**，杜绝“两个地方都写进度、互相打架”。
2.  **门禁脚本化 = 可复现基线**：把“是否满足安全属性”写成可重复运行的门禁脚本 `pi-security-validate-windows.ps1`（Windows 53/0）与 `pi-security-validate-linux.sh`（Linux 35/0），任何人任何机器一键复现，替代“人工肉眼核对”。
3.  **多机矩阵**：合规不能只在一台机器绿。用三机（Win11/Server2022/Server2025）+ 四机（default/custom 路径）+ 双 Linux（Ubuntu/RHEL）矩阵验证，专门逼出“只在某组合下暴露”的坑（如默认路径继承只读 ACL，见 [`06` 第六节](../3-postmortems/security-hardening.md)）。

> 教训一句话：**合规整改的交付物不是“改好的代码”，而是“可复现的证明”**——把验收标准固化成门禁脚本 + 多机矩阵，才经得起外部审。

### 方法论六：安全决策的“做减法”——用威胁模型和爆炸半径算账（安全整改催生）

功能开发的直觉是“多做 = 更好”；安全整改恰恰相反——**“更安全”不等于“该做”**。加固往往有成本、有回归风险，若不落在真实威胁路径上，做了只是增加维护面。沉淀出一条决策纪律：**任何加固/残余风险，先用威胁模型 + 爆炸半径算账，再决定做还是不做**。

*   **论证“不做”**：SNMP 专用密钥（7-1）——现状已机器绑定 HKDF 加密、每实例唯一，唯一真实威胁是 nonce 泄露，换专用钥“增益≈0 且有明文回归风险”→ **坚决不做**。
*   **论证“接受残余风险”**：去硬编码后改“空默认口令 + 首登强制改密”，引入极短的“抢注窗口”——评估后**接受**（私有化受控网络 + 首登即关闭窗口，远小于“继续用全网已知硬编码口令”的风险）。
*   与方法论四（证伪）互补：证伪是“别把直觉假设当结论”，做减法是“别把直觉加固当必需”。

> 教训一句话：**敢于有理有据地说“不做”，和把该做的做对同样重要**——把有限的工程资源花在真正降低风险的地方。

## 三、 实战案例一：AI 协同解决“解压工具崩溃”的演进过程

以下案例真实还原了在本次重构中，如何运用上述方法论引导 AI 步步为营，最终攻克“GnuWin32 unzip.exe 静默崩溃”这一隐蔽 Bug 的全过程。

### 1. 初始阶段（AI 给出常规建议，遭遇黑盒崩溃）
*   **问题**：在现代 Windows 运行环境下，解压 PostgreSQL 介质时，安装器无任何报错，但 `database` 目录下文件严重缺失，导致后续 `initdb` 报错。
*   **AI 常规建议**：使用开源的 GnuWin32 `unzip.exe` 进行解压。
*   **运行结果**：`unzip.exe` 在某些 Windows Server 2019+ 机器上静默退出（Exit Code 0，但实际未解压完），无任何 STDERR 输出。

### 2. 推理阶段（引导 AI 分析底层依赖）
*   **证据输入**：我们将 `unzip.exe` 的系统调用和 DLL 依赖信息提供给 AI。
*   **AI 深度推理**：AI 通过分析发现，GnuWin32 的 `unzip.exe` 编译于极古老的年代，强依赖 `msvcp60.dll`。而在现代安全的 Windows 操作系统中，该 DLL 默认不被信任或缺失，导致其在解压大文件时发生静默内存截断。
*   **破局方案**：AI 提出，Windows 10 (1803+) 和 Windows Server 2019+ 已经原生内置了现代的 `tar.exe`（基于 BSD tar），支持直接解压 `.zip` 格式，且没有任何外部古老 DLL 依赖。

### 3. 实施与安全闭环（AI 编写防御性代码）
*   **安全沙箱介入**：我们要求 AI 编写升级为 `tar.exe` 的解压命令，同时必须通过 `verify-destructive-commands.ps1` 的安全审计。
*   **最终生成的极简、安全且极其稳定的解压命令**：
  ```cmd
  tar -xf "$USER_INSTALL_DIR$$\\pgsql.zip" -C "$USER_INSTALL_DIR$$\\"
  ```
*   **Fail-Fast 机制**：为了防止在极少数不支持 `tar.exe` 的旧系统上运行失败，引导 AI 在 Java Custom Code `GetApplicationNames.java` 中编写了前置静默兼容性检查，完美实现工程闭环。

## 四、 实战案例二：AI 协同排查“ZE 服务链执行断层”的逆向推导

在 `build-5` 到 `build-11` 期间，我们遭遇了“Zero Engine 文件已落盘，但服务注册动作从未执行”的严重断层。以下是引导 AI 进行逆向推导并最终破局的硬核过程。

### 1. 初始阶段：控制变量与 Diff 对照
*   **问题**：`build-5` 构建成功，但装机时没有执行任何 `ZESvc` 注册命令。
*   **引导 AI 推理**：我们向 AI 提供了 `build-5.txt` 构建日志、安装日志 `PI_安装_05_27_16_21_41.log` 以及 `TAFCore.iap_xml` 的相关片段。
*   **AI Diff 分析**：
    *   对比正常的 `TAFsvc` 注册步骤，发现 `ZESvc` 的动作组 `ecdb7d1e9e76` 在安装日志中被**静默跳过**，没有任何“开始执行”或“执行失败”的标记。
    *   检查 XML 结构，发现 `ecdb7d1e9e76` 组在 XML 中的物理定义，其父节点是 `TAF DB Linux` 组件（objectID `60769435ad62`），而在 Windows 专属序列中，仅仅是通过一个 `<object refID="ecdb7d1e9e76"/>` 进行了引用。

### 2. 规律推导：IA 编译器的黑盒组件隔离限制
*   **AI 逻辑推导**：
    *   InstallAnywhere 在运行时会根据用户选择的特性（Features）和组件（Components）来动态构建执行树。
    *   如果一个动作组的**物理定义**位于一个未被激活的组件（如 Linux 专属组件）下，即使它在已激活组件（如 Windows 专属组件）的执行序列中被引用，运行引擎也会因为该组件未激活而**静默忽略该动作组的全部子动作**。
    *   这就是典型的**“跨组件引用静默失效”**黑盒行为。

### 3. 方案演进与闭环（v6 到 v7 修复）
*   **AI 提出的重构策略**：必须将 `ecdb7d1e9e76` 动作组的物理定义进行“提升（Hoist）”，使其脱离 Linux 组件，直接内联到 Windows 专属的 `d4095d81b09b` 序列中。
*   **编写自动化补丁**：引导 AI 编写了 `apply-ze-install-fix-v7.py` 脚本，通过 Python 的 XML 解析器，自动在 XML 中完成以下重构：
    1.  定位 `ecdb7d1e9e76` 动作组。
    2.  将其从 Linux 组件的 `visualChildren` 向量中删除。
    3.  将其完整定义内联插入到 `d4095d81b09b` 向量的 `zeroengine` 文件落盘动作之后。
    4.  移除所有上层孤立的 `refID` 引用。
*   **运行结果**：`build-11` 装机验证中，`ZESvc` 注册、JRE 解压、服务启动等动作**首次全部 100% 顺利执行**，完美攻克了这一黑盒断层。

## 五、 实战案例三与案例四：Linux 双平台攻坚

将安装器从单 Windows 扩展到 RHEL + Ubuntu 双平台时，我们又遭遇了两个典型黑盒问题。以下沿用“初始阶段 → 推理阶段 → 实施与闭环”的三段式，还原 AI 协同破局的过程。深度机理见 [`02-hardcore-technical-postmortems.md`](../3-postmortems/migration-and-platform.md) 第六章。

### 实战案例三：AI 协同定位 IA `$…$` 内联脚本吞噬（同一坑复发两次）

#### 1. 初始阶段（本地静态通过，实机却崩）
*   **问题**：写在 IA 内联 ExecuteScript 里的 Linux 脚本，本地 `bash -n` **完全通过**，实机执行却报 `unexpected EOF while looking for matching '"'`，Zero Engine / PostgreSQL 一步没跑；后来的 OS 白名单判定脚本同样“本地对、实机错”，**RHEL 9.7 与 Ubuntu 26.04 双双误判 `OS not supported`**。
*   **AI 常规建议（无效）**：一开始 AI 顺着 `unexpected EOF` 建议“检查引号是否配对”“加转义”，反复调引号都无效——因为源文本里的引号本就是配对的。

#### 2. 推理阶段（用旁证引导 AI 跳出表象）
*   **证据输入**：我把关键旁证喂给 AI——“同一组里**不含** `$` 的 `grep PRETTY_NAME/VERSION_ID` 一直正常，唯独**带裸 `$`** 的这段脚本挂”。
*   **AI 深度推理**：引导其对照差异后，AI 推导出黑盒规律：IA 打包时按出现顺序**成对切分** `$…$`；当**同一物理行 `$` 总数为奇数**时（如 `$BASH_VERSION` 的 1 个 `$` + 8 个 `$USER_INSTALL_DIR$` = 17 个），孤立的 `$BASH_VERSION` 会**偷走相邻 `$USER_INSTALL_DIR$` 的开头 `$`**，导致全行配对错位、双引号被拆成奇数 → bash `unexpected EOF`。

#### 3. 实施与闭环（外置 + 零 `$`）
*   **破局方案**：把逻辑**外置为独立 `.sh`**（随 `InstallDirectory` 目录型打包，无新增 objectID、无剥离风险）；OS 判定改为**零 `$` 的 grep 管道**。
*   **沉淀铁律**：“**IA 内联 ExecuteScript 禁写裸 shell `$` 变量**”，并写入结构门禁断言；同时明确“`bash -n` 不覆盖 IA `$` 替换层，必须实机验证”。

### 实战案例四：卸载器 exit 218 黑盒的证伪式排查 → 果断脱钩

#### 1. 初始阶段（黑盒无输出）
*   **问题**：Linux 上运行 `trellisappmgruninstall` 直接 **`exit 218`**，无任何 stdout/stderr、无日志文件——真错被 LaunchAnywhere native 启动器吞掉。
*   **直觉假设（危险）**：“IA 用的是 Java 21，多半是 Java 21 不兼容”。

#### 2. 推理阶段（先证伪，再定位）
*   **不顺直觉猛冲**：我要求先**证伪**假设，而不是立刻去折腾 JVM 版本。
*   **AI 协同证伪**：用同版本 IA **安装器**的 `lax_dump` 证明它在 **Zulu 21 上能完整跑完** → 直接推翻“Java 21 不兼容”，把问题精确锁定到**卸载器 native 启动器的 JVM 引导阶段**（真错被吞），而非 Java 运行时本身。

#### 3. 实施与闭环（架构级脱钩）
*   **破局方案**：既然黑盒难定位，果断**脱钩**——用 shell **shim** 替换 native 卸载器，以 `pi-linux-uninstall.sh` 作为**单一事实源**，安装失败回滚复用同一脚本。前提是 **Windows 卸载链零回归**（`IsLinux` 门控）。
*   **沉淀理念**：“**黑盒工具在新平台失败点难定位时，保住旧平台的前提下，果断解耦重写往往优于逆向死磕**”。

## 六、 实战案例五与案例六：安全整改攻坚

安全整改期间又出现两个典型的“方法论现场”，一个印证方法论四（证伪），一个印证方法论六（做减法）。深度机理见 [`06-security-hardening-postmortems.md`](../3-postmortems/security-hardening.md)。

### 实战案例五：AI 协同定位“WSL 幽灵 5432”——先证伪，别冤枉新改动

#### 1. 初始阶段（新改动 + 新故障，直觉甩锅）
*   **问题**：Windows 服务降权后，实机反复“`TAFdb` 服务消失 / 卡建库 / 空日志”。
*   **危险直觉**：“肯定是刚做的 6-2 锁死了 PGDATA、`LocalService` 靠服务 SID 进不去”——差点回滚整段降权。

#### 2. 推理阶段（用证伪跳出“新改动有罪”）
*   **不顺直觉猛冲**：先证伪“降权锁死”假设，而不是回滚。
*   **AI 协同证伪**：换端口/换机器后故障消失 → 推翻降权有罪，把矛头转向“**5432 被占**”。真凶是 **WSL2+Docker 里的 postgres 占了 5432**，经 WSL2 localhost 转发暴露到 Windows `127.0.0.1:5432`，`TAFdb` 绑不上报 `FATAL: could not create any TCP/IP sockets`。**诊断陷阱**：`netstat`/`Get-NetTCPConnection` **看不到 WSL 转发的监听者**（TCP 直连却通），把“端口没被占”的假象坐实了误判。

#### 3. 实施与闭环（工具盲区写进前置检查）
*   **破局**：降权改动（`LocalService`/`sidtype`/6-1/6-2）被证明**全部正确、无需回滚**；把“装前确认 `5432/8443/8088/162` 未被占（尤其 WSL2/Docker）”写进 QA 前置。
*   **沉淀理念**：“**新改动 + 新故障，先证伪、再定性；工具说‘没占用’不等于真没占用**”——与 `lax_dump` 推翻“Java 21 不兼容”同型。

### 实战案例六：AI 协同做“减法决策”——SNMP 专用密钥该不该做？

#### 1. 初始阶段（一个“听起来更安全”的提议）
*   **问题**：SNMP 凭据要不要从 `GENERAL` 钥换成专用 `vertiv-pi-snmp-v1` 做域隔离？直觉上“专用钥更干净、更安全”。

#### 2. 推理阶段（引导 AI 做威胁模型，而非附和）
*   **不附和直觉**：要求先建威胁模型，而不是直接开做。
*   **AI 协同算账**：现状 SNMP 凭据**已**用机器绑定 HKDF `GENERAL` 钥（每实例唯一、AES-256-GCM）加密，已满足 SEC-REQ；专用钥与 GENERAL **同源同 nonce**、`info` 标签代码公开，**唯一真实威胁（nonce 泄露）来时两把钥一起沦陷** → 专用钥**增益≈0**，且改造有明文回归风险。

#### 3. 实施与闭环（写清论证，坚决不做）
*   **破局方案**：**不做**，并把“增益≈0 + 风险>0”的论证写进路线图 N-26；后续有硬需求再走“modifier 带 purpose”的低风险路线。
*   **沉淀理念**：“**用威胁模型 + 爆炸半径算账，敢于有理有据地不做**——把资源花在真正降险处”。

## 七、 总结：给未来重构者的建议

1.  **不要让 AI 盲目写代码**：在动手前，先让 AI 帮你梳理系统拓扑和依赖关系。
2.  **提供“好代码”作为模板**：AI 是极佳的模仿者。给它一段写得非常严谨、防御性极强的脚本，它就能源源不断地生成同样高品质的代码。
3.  **用工具约束 AI**：永远不要相信 AI 保证的“这段代码绝对安全”。用静态审计脚本、编译器校验和 CI 门禁来做最后的把关。
4.  **跨平台扩展先证伪假设**：用 dump / 旁证推翻直觉误判（如“Java 21 不兼容”），避免朝错误方向投入。
5.  **认清静态验证的边界**：IA `$` 替换层与离线依赖链**必须实机验证**，静态全绿 ≠ 能跑。
