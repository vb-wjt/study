# Hazelcast

## 概述

```text
- 一个用 Java 编写的内存数据网格(IMDG)
- 核心功能: 将数据(如 Map, Queue等) 分布到集群中多个节点的内存里面, 使得应用可以像操作本地集合一样操作分布式数据
- 最大优点: 无需引入外部数据库/中间件(如 redis), 只需要引入一个 JAR 包, 配置集群, 就能让多个应用实例形成一个分布式缓存/数据层
```

## 在 SI 中的作用

1. 分布式缓存(内存表, IMap 监听器, ITopic发布订阅机制等)
2. 分布式锁 (IMap<String, String> locks)
3. 分布式任务执行
4. 多优先级执行器服务
5. 集群发现和网络配置
6. 负载均衡机制
7. 队列监听机制

```text
1. 监听器订阅 ITpoic, 当向 ITopic 中发消息时, 监听器根据 socketId 往对应浏览器 websocket 客户端发送消息, 实时通知 SI 的设备状态
2. 使用 IMap 来实现分布式锁; 
    - IMap<String, String> locks; // 存放锁 
    - locks.lock(lockName); // 加锁
    - locks.unlock(lockName); // finally 里面释放锁 

```

## 相关概念

### 1. IMDG

IMDG(In-memory Data Grip, 内存数据网络); <br>
不是一个简单的缓存, 是一个由网络连接的多个节点的内存组成的统一数据层; <br>
所有的操作主要在内存中完成, 速度极快; <br>
数据不是存在一个地方, 实际上是由集群里面的每个节点的部分内存组成的一块区域, 根据规则(哈希算法)分散存放在各个机器,
而因为是跨机器的, 所以其实相当于一块 "虚拟内存"; <br>
操作数据时, 只需要和本地的 HazelcastInstance 交互, 它充当一个智能代理, 负责计算键的分区, 查找分区所有者(如果是本地机器就直接访问机器,
非本机则发网络请求); <br>

### 2. ITopic

#### 2.1 作用

发布订阅模式, 极致的速度和低延迟的广播, 默认不进队列, 也不持久化; 用于实时消息, 比如 webSocket 推送;

#### 2.2 ITopic 的广播实现

```text
Hazelcast 构建在一个集群之上，每个节点都知道其他节点的存在。当 ITopic.publish()被调用时，其广播流程如下：
1.事件封装： 消息和主题名被封装成一个内部事件对象。
2.集群通信层： 这个事件被交给 Hazelcast 的自定义集群通信层。这个层是 Hazelcast 的核心，它维护着所有节点的连接和成员列表。
3.组播/广播模拟： 该通信层并不真正使用网络层的广播（如UDP广播），因为这在广域网或云环境中通常不可靠且被禁止。相反，它使用一种基于TCP的、可靠的点对点组播模拟。
    • 系统会遍历所有活跃的集群节点列表。
    • 通过已有的TCP连接，将这个事件消息单独发送给每一个节点。这是一种“伪广播”，非常可靠。
4.本地派发： 每个节点收到这个事件后，并不需要再去网络上去取消息。它直接在本地内存中查询有哪些监听器（MessageListener）注册了这个主题，然后使用本节点的线程池异步地调用这些监听器的 onMessage方法。
```

#### 2.3 核心特点

```text
•极速： 消息的传递路径是：发布者 -> 网络 -> 每个节点的本地内存。没有中间的存储、序列化、持久化到磁盘的开销。
•内存网络： 整个流转过程都在内存和网络间完成，延迟极低。
•无中间状态： 消息本身在派发后不会在 Hazelcast 中留下任何状态（除非配置了持久化）。它的生命期就是传递的过程。
```

#### 2.4 为什么不像 Kafka 那样用队列实现 ?

这是一个关于设计目标和权衡的经典案例。Kafka/RocketMQ（以下简称MQ）和 Hazelcast ITopic是为完全不同的场景而生的。

##### 2.4.1. 核心范式与设计目标

|        | Hazelcast ITopic              | Kafka / RocketMQ             |
|--------|-------------------------------|------------------------------|
| 核心范式   | 广播 (Broadcast)                | 队列 (Queue) / 发布-订阅 (Pub-Sub) |
| 设计目标   | 极低延迟、进程间事件通知                  | 高吞吐、持久化、解耦、流处理               |
| 消息模型   | “发后即忘” (Fire-and-Forget)      | “持久化日志” (Persistent Log)     |
| 最佳应用场景 | 集群内状态变化通知、实时仪表盘数据推送、分布式缓存失效通知 | 业务订单处理、用户活动追踪、数据管道、流处理分析     |

##### 2.4.2 消息传递的语义与可靠性

```text
•ITopic(默认)：最多一次 (At-most-once)
•消息发出后，不保证一定能送达。如果某个节点在消息广播后、处理前宕机了，那么该节点上的订阅者就会丢失这条消息。
•为什么？ 因为追求速度，它不做复杂的确认和重发机制。适合那些“丢一条消息也无伤大雅”的场景，例如实时更新一个监控界面的CPU使用率数字。

•Kafka：至少一次 (At-least-once) / 精确一次 (Exactly-once)
•持久化： 所有消息都被追加写入到磁盘的日志文件中，并会被复制到多个副本（Replicas）上。即使服务器宕机，消息也不会丢失。
•确认机制： 消费者（Consumer）需要处理完消息后，向Kafka提交一个偏移量（Offset），表示“我已经成功处理到了这个位置的消息”。如果消费者崩溃，它可以重启并从上次提交的偏移量继续消费。
•这种机制保证了消息绝不会因为系统故障而丢失，但可能会被重复处理（如果消费者处理完但提交偏移量前崩溃），故为“至少一次”。
```

##### 2.4.3 状态与扩展性

```text
•ITopic： 无状态
•它不保留消息的历史。一个新加入的订阅者只能收到它加入之后发布的消息，无法获取之前的历史消息。
•扩展性受限于广播风暴。如果集群有1000个节点，每条消息都需要被复制1000份。节点越多，广播的网络开销越大。

•Kafka： 有状态
•它将所有消息持久化一段时间（例如7天）。新加入的消费者可以回溯消费之前任意时间点的消息。
•扩展性极佳。通过分区（Partition） 机制，一个Topic的数据可以分散到多个服务器上。消费者以组（Consumer Group）的形式工作，每个分区只被组内的一个消费者消费，从而实现水平扩展和负载均衡。增加消费者和服务器就能增加整体吞吐量。
```

##### 2.4.4 一个生动的比喻

```text
Hazelcast ITopic：像一个现场扩音系统。演讲者（发布者）对着麦克风说话，所有在现场（集群内）的人（订阅者）此时此刻都能听到。声音是瞬时的，无法回放。如果有人晚到，就错过了之前的讲话。
Kafka：像一个高保真录音棚。演讲者（发布者）的讲话被完整录制下来（持久化到日志）。听众（消费者）可以随时来听录音（消费），可以暂停、快进、重听昨天的内容（重置偏移量）。录音带可以被复制多份（副本）以防损坏，并且可以分给很多人同时听不同的部分（分区和消费者组）。
```

##### 2.4.5 结论与选择

```text
•使用 Hazelcast ITopic当：
•你需要微秒/毫秒级的延迟。
•消息是瞬时的、事件性的，丢失一两条可以接受。
•你的应用场景是一个集群内部的实时通知和协同。
•例如：WebSocket设计、分布式缓存失效、集群内状态同步。

•使用 Kafka/RocketMQ 当：
•你需要消息持久化，绝不能丢失。
•你需要消费者能够回溯历史消息或按照自己的节奏处理。
•你的系统需要解耦，生产者和消费者生命周期不同，速率不同。
•数据流量非常大，需要高吞吐和水平扩展。
•例如： 订单处理流水线、用户行为日志收集、将数据库变更同步到搜索引擎。
```

### 3. 分布式锁

#### 3.1 SI 中的实现 IMap (com.hazelcast.map.impl.proxy.MapProxyImpl#lock(K))

```text
com.hazelcast.map.impl.proxy.MapProxyImpl#lock(K) 提供的是基于数据行的悲观锁;
    - 对 IMap 中的某一个 key 对应的 value 进行 "读-修改-写" 这一系列操作时, 加锁保证操作的原子性和隔离行, 防止其他线程干扰;
    - 假如并发冲突是很可能发生的, 在操作数据之前就先获取锁, 把数据 "锁住", 悲观锁
    - 锁的粒度是单个 key; 可以同时锁住 key1 和 key2, 互不干扰. 这与锁住整个 IMap 完全不同;
```

#### 3.2 IMap 实现分布式锁的问题

```text
- 官方文档通常不推荐使用 IMap.lock(lockName) 来作为分布式锁;
- 容易导致死锁; 
    - 因为它是不可重入的. 如果一个方法 a() 获取了锁; 然后调用另外一个方法 b(), 而 b() 也尝试获取同一个锁, 那么线程就会在 b() 中永远阻塞, 导致死锁; 这在复杂代码中很容易意外发生;
- AP 系统的风险;
    - hazelcast 默认是 AP, 网络分区可能导致锁状态在不同分区中不一致, 从而可能破坏期望的原子性
- 如果是为了保护 IMap 中的数据, 有更好的替代方案; EntryProcessor 几乎是严格优于 IMap.lock(lockName) 的解决方案
    - EntryProcessor 将操作代码发送到数据所在节点执行, 天生就是原子的, 不需要显示加锁解锁
    - 性能更高(只有一次网络往返)
    - 避免了手动管理锁带来的所有风险(如忘记解锁, 不可重入死锁)
- 如果是为了实现分布式锁, 可以使用 Hazelcast 默认提供的 ILock, 经过官方充分测试的.
```

IMap 和 ILock 的区别:
```text
flowchart TD
    A[ Hazelcast 提供的锁 ] --> B[IMap.lockkey<br>数据行级悲观锁]
    A --> C[独立 ILock<br>通用分布式协调锁]

    B --> B1[设计初衷<br>保护对IMap中特定数据的并发访问]
    B --> B2[粒度<br>极细: 单个Key]
    B --> B3[应用场景<br>银行账户余额更新<br>商品库存扣减]

    C --> C1[设计初衷<br>保护任何分布式临界资源<br>或协调流程]
    C --> C2[粒度<br>较粗: 整个业务逻辑或资源]
    C --> C3[应用场景<br>分布式任务调度<br>防止重复处理<br>集群内主节点选举]
```

#### 3.3 ILock

##### 3.3.1 ILock 是 Hazelcast 的分布式数据结构之一, 实现紧密依赖其 IMDG 架构

##### 3.3.2 数据基础

```text
- 锁存储在 IMDG 中, 但是是 特殊的, 非分区, 强一致性 的 Hazelcast 数据结构中(可以理解为只有一条记录的, 集群共用的 IMap)
- 锁本质上是一个共享状态(当前哪个成员持有锁, 重入次数, 锁名称等)
- 这个数据结构的所有读写操作都是线性化的 (Linearizable), 保证了操作的原子性和顺序一致性, 这是实现锁的基础.
```

##### 3.3.3 核心机制

```text
- Hazelcast 默认是 AP 系统(优先保证可用性), 但分布式锁 ILock 的实现依赖于内部的 CP (一致性+分区容错性) 子系统(基于 Raft 共识算法)
- 当一个节点尝试获取锁时, 请求会被发送到 CP　组的　Raft 主节点
- Raft 主节点会以强一致的方式顺序处理所有获取锁, 释放锁的请求, 确保在集群中所有节点看来, 锁的状态都是一致的
```

##### 3.3.4 特性与 API

```text
- 可重入: 与 Java 的 ReentrantLock 类型, 同一个线程可以多次获取同一把锁
- 公平锁: Hazelcast 锁默认是公平的, 按照请求到达 CP 组的顺序授予锁, 防止饥饿
- 租期(Lease) : 锁可以设置租期时间, 防止因持有锁的客户端崩溃而导致锁永远不被释放
- 监听器: 可以添加监听器来监听锁被释放的时间, 从而实现简单的通知机制
```

```java
class Lock {
    HazelcastInstance hz = Hazelcast.newHazelcastInstance();
    ILock lock = hz.getLock("my-distributed-lock");

    public void lock() {
        // 尝试获取锁，最多等待10秒
        if (lock.tryLock(10, TimeUnit.SECONDS)) {
            try {
                // 成功获取锁，执行关键代码段
                System.out.println("Doing work under lock...");
            } finally {
                // 必须 finally 中释放锁
                lock.unlock();
            }
        }
    }
}
```

##### 3.3.5 ILock 与 Redis, Zookeeper 的对比

| 特性      | Hazelcast           | Redis (RedLock)     | ZooKeeper         |
|---------|---------------------|---------------------|-------------------|
| 实现基础    | 内置 CP 子系统 (Raft)    | AP 系统上的算法 (RedLock) | CP 系统 (ZAB协议)     |
| 锁的本质    | 集群内强一致的状态           | Key的随机值设置           | 临时顺序节点            |
| 一致性保证   | 强一致 (线性化)           | 弱一致 (异步复制)          | 强一致 (顺序一致性)       |
| 性能      | 高 (内存操作，但需Raft共识)   | 极高 (内存操作，无共识开销)     | 较低 (需写磁盘日志，节点间广播) |
| 可靠性/安全性 | 高 (基于Raft，官方维护)     | 有争议 (对时钟、延迟敏感)      | 最高 (基于ZAB，精心设计)   |
| 死锁处理    | 租期超时自动释放            | 锁key过期自动释放          | 会话结束临时节点自动删除      |
| 额外依赖    | 无 (IMDG内置功能)        | 无 (但需独立Redis服务)     | 无 (但需独立ZK集群)      |
| 生态结合    | 与Hazelcast IMDG无缝集成 | 与Redis缓存/存储生态结合     | 与ZK的协调生态结合        |


##### 3.3.6 ILock 与 Redis, Zookeeper 各自适合的场景
1. Hazelcast ILock
```text
适用场景：
• 已经在使用 Hazelcast IMDG： 这是最自然的选择。你不需要引入新的外部依赖，锁与你的缓存、数据共享在同一个集群中，运维简单。
• 需要高性能的强一致锁： 应用既需要很高的吞吐量和低延迟，又需要强一致的锁保证。Hazelcast 在性能和一致性之间取得了较好的平衡。
• Java 原生体验： 希望使用类似 java.util.concurrent.locks.Lock的标准接口。

不适用场景：
• 技术栈中没有 Hazelcast。
• 环境对资源极其敏感，无法承担 Hazelcast 节点的内存开销。
```

2. Redis (RedLock 算法)
```text
适用场景：
• 极致性能场景： 对锁的性能要求极高，可以接受在极端情况下（如网络分区、时钟跳跃）的少量风险。例如：秒杀、抢购等高频并发场景，其目标是极大程度地减少库存，而不是保证绝对不超卖。
• already using Redis： 项目已经为了缓存等功能部署了 Redis 集群，希望复用基础设施。
• 锁的可靠性要求可接受风险： 锁保护的资源非关键，即使偶尔失效也不会造成灾难性后果。

不适用场景：
• 需要绝对正确性： 在金融交易、订单处理等要求绝对正确的场景下，RedLock 的争议性使其可能不是一个最佳选择。
• 系统环境不可控： 存在严重的网络延迟或时钟不同步的风险。
```

3. ZooKeeper
```text
适用场景：
• 需要绝对可靠和正确： 锁的 correctness 是首要目标，性能是次要考虑因素。例如：主节点选举、分布式资源分配、确保不会发生双写冲突。
• already using ZooKeeper： 你的系统已经依赖 ZooKeeper 进行服务发现、配置管理等（例如在 Kafka、Hadoop 生态中）。
• 基于事件的监听： 需要利用其 Watch 机制来监听锁的释放情况，实现更复杂的协调流程。

不适用场景：
• 高性能场景： 对锁的获取和释放速度有极高要求，无法接受其写磁盘和广播协议的开销。
• 简单场景： 仅仅需要一个简单的锁，引入一个沉重的 ZooKeeper 集群显得杀鸡用牛刀。
```

4. 总结
```text
• 选 Hazelcast Lock： 已经身处 Hazelcast 生态，需要一个性能不错且可靠的锁，希望运维简单。
• 选 Redis Lock： 追求极致性能并能承担一定的风险，或者已经大规模使用 Redis。
• 选 ZooKeeper Lock： 需要绝对的正确性和可靠性，并且愿意为此牺牲一些性能。
```


### 4.补充:
#### Raft
Raft 是什么？

Raft 是一种共识算法。它的目的是在分布式系统中的多个节点之间就某个值（或状态变更）达成一致，即使在部分节点故障或网络出现分区的情况下也能正常工作。

它的核心思想是“领导人与日志复制”：

1.
在一个集群中，任何一个时刻只有一个领导人（Leader）。

2.
所有客户端的写请求都必须发送给领导人。

3.
领导人将写操作作为一条日志条目（Log Entry） 复制给其他追随者（Follower） 节点。

4.
一旦大多数节点（过半，如3节点中的2个）成功复制了日志，领导人就提交（Commit） 该条目，并将其应用到自己的状态机中，并通知追随者也应用该条目。

5.
这样，整个集群的状态就以强一致的方式向前推进。

有 Raft 和没有 Raft 的区别与影响：

有 Raft (CP 系统, 如 ILock)

无 Raft (AP 系统, 如 默认IMap)

一致性

强一致。所有操作线性化，数据永远最新。

最终一致。数据异步复制，可能读到旧值。

可用性 during Partition

可能不可用。如果无法形成“大多数”（如3节点断了2个），则无法处理写请求，甚至会拒绝读请求，优先保数据一致。

始终可用。每个分区内的节点仍可独立处理读写请求，优先保服务可用，但分区间的数据会不一致。

性能

较低。需要日志复制和多数节点确认，网络往返多，延迟高。

较高。通常只需写入主节点即可返回，延迟低，吞吐高。

使用场景

分布式锁、领导者选举、分布式协调（要求绝对正确性）。

缓存、会话存储、实时统计（允许短暂不一致）。
