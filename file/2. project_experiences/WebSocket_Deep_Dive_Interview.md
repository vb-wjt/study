## 一、Spring WebSocket 连接关闭触发机制

### 1.1 提问：浏览器什么操作会导致后端 `afterConnectionClosed` 执行？

**核心回答：**
当浏览器端的 WebSocket 连接以任何方式终止时，服务端的 `AbstractWebSocketHandler` 的 `afterConnectionClosed` 方法最终都会被调用。无论关闭是由谁发起、通过什么方式（正常还是异常），该方法都是服务端进行连接后清理工作的统一入口。

### 1.2 触发场景汇总表

| 触发场景 | 具体操作 | 服务端 CloseStatus | 状态码说明 | 触发性质 |
| :--- | :--- | :--- | :--- | :--- |
| **🛑 用户主动关闭页面/标签** | 关闭浏览器标签页、输入新地址跳转、刷新页面 | `CloseStatus.GOING_AWAY` (**1001**) | **端点离开**：用户正在离开当前页面或关闭浏览器。 | **正常关闭**（但用户无感知） |
| **🖱️ 脚本主动关闭连接** | 在 JavaScript 中调用 `socket.close()` | `CloseStatus.NORMAL` (**1000**) | **正常关闭**：连接已完成目的，由代码显式发起。 | **正常关闭** |
| **🌐 网络连接中断** | 网络断开、Wi-Fi 切换、进入飞行模式、服务器端网络故障 | `CloseStatus.NOT_CONNECTABLE` (**1006**) | **异常关闭**：没有收到关闭帧，表示底层 TCP 连接意外断开。 | **异常关闭** |
| **⏱️ 空闲连接超时** | 连接建立后，双方长时间无数据交换，达到服务端设置的超时阈值 | 服务端配置的默认值 | **正常关闭**：服务端为释放资源，主动清理空闲连接。 | **正常关闭**（服务端主动） |
| **⚠️ 协议错误/数据格式错误** | 客户端发送了不符合协议规定的数据（如错误的帧格式） | `CloseStatus.PROTOCOL_ERROR` (**1002**) | **协议错误**：由于协议层面的问题导致连接无法继续。 | **异常关闭** |

### 1.3 CloseStatus 参数解析

`afterConnectionClosed` 方法接收的 `CloseStatus` 包含关闭详情：
*   `code`: 关闭状态码（如 1000, 1001, 1006）。
*   `reason`: 关闭原因（可选，UTF-8 字符串，对于 1006 通常为空）。
*   **注意**：对于 `1006` 这类异常关闭，`reason` 字段通常为空，主要依赖 `code` 判断。

## 二、浏览器端 1006 状态码的捕获

### 2.1 提问：前端能捕获到 1006 状态码吗？

**核心回答：**
是的，前端完全可以捕获。通过监听 WebSocket 的 `close` 事件并检查 `CloseEvent` 对象的属性即可。

### 2.2 捕获示例代码

```javascript
socket.addEventListener('close', (event) => {
  console.log(`关闭代码: ${event.code}`);
  console.log(`关闭原因: ${event.reason || '(无原因)'}`);
  console.log(`是否正常关闭: ${event.wasClean}`);

  // 专门处理 1006 异常关闭
  if (event.code === 1006) {
    console.error('⚠️ WebSocket 连接异常断开 (1006)');
    console.error('可能原因：网络中断、服务器崩溃、超时等');
    reconnectWebSocket(); // 执行重连逻辑
  }
});
```

### 2.3 关键属性说明

*   **`code`**: 关闭状态码。1006 表示异常断开。
*   **`reason`**: 对于 1006，这个值通常为**空字符串**，因为错误来自本地浏览器实现，而非服务器。
*   **`wasClean`**: 对于 1006，这个值恒为 **`false`**。

## 三、安全软件切换导致 1006 异常的深度分析

### 3.1 提问：切换安全软件后，浏览器和服务端的状态是什么？

**核心回答：**
此时两端都处于 **"连接已死"** 的状态。
*   **浏览器端**：底层 TCP 连接被强制中断或失效，JS 层 `readyState` 变为 `CLOSED` (3)。
*   **服务端**：底层 TCP 连接检测到异常，Spring 触发 `afterConnectionClosed`，状态码为 1006。
*   **本质**：就像打电话时电话线被突然拔掉（RST）或信号完全消失，双方都没来得及说“再见”。

### 3.2 现象解析：为什么有时立即断开，有时拖了 6 分钟？

#### 现象一：快速结束（时间 ≈ 消息间隔）
*   **原因**：安全软件（VPN）在切换配置时，向操作系统发送了信号，或向网络中发送了 **TCP RST（复位包）**。
*   **过程**：VPN 软件立即通知操作系统“之前的连接都作废了”，浏览器 Socket 立刻收到通知并触发 close。
*   **比喻**：对方直接挂断电话，你立刻听到忙音。

#### 现象二：慢速结束（持续 6 分钟）
*   **原因**：发生了**静默中断**。旧的 VPN 隧道被直接拆除，但没有发送任何通知（RST）。数据包发出去像进入黑洞，有去无回。
*   **过程**：
    1.  最后一条消息是 1.3 分钟前发的。
    2.  此后 1.3 分钟到 6 分钟，连接是**空闲的（Idle）**，没有新消息，也没有心跳。
    3.  **TCP 协议特性**：TCP 默认不因收不到数据就断开（可能只是拥塞）。
    4.  **6 分钟的真相**：操作系统的 TCP 保活探测（Keep-Alive）或 VPN 客户端/中间件的“死连接检测”定时器（如 360 秒）到期，强制杀死了连接。
*   **结论**：延迟是因为**连接空闲**，没有应用层数据触发失败检测。

## 四、WebSocket 协议原理与 TCP 关系

### 4.1 核心关系图解

| 层次 | 协议 | 角色 |
| :--- | :--- | :--- |
| **应用层** | **WebSocket** | 全双工、有状态、基于帧通信。**一次 HTTP 握手升级后，复用 TCP 连接**。 |
| **应用层** | **HTTP** | 半双工（请求-响应）、无状态。仅用于 WebSocket 握手阶段。 |
| **传输层** | **TCP** | 提供可靠的、面向连接的字节流管道。WebSocket 运行在 TCP 之上。 |

### 4.2 WebSocket 生命周期

#### 1. 握手建立 (HTTP Upgrade)
客户端发送带有特殊 Header 的 HTTP GET 请求：
*   `Upgrade: websocket`
*   `Connection: Upgrade`
*   `Sec-WebSocket-Key: [随机字符串]`
服务端返回 HTTP 101 Switching Protocols，握手成功，连接升级。

#### 2. 数据传输 (帧通信)
数据以 **帧** 的形式传输。
*   **帧结构**：包含 FIN（结束标志）、Opcode（操作码，如 0x1 文本, 0x2 二进制, 0x8 关闭）、MASK（掩码）、Length、Payload Data。
*   **特点**：支持分片传输；客户端发送的帧必须掩码处理。

#### 3. 关闭断开
*   **正常关闭**：一方发送 Close 帧（含状态码，如 1000），另一方回应 Close 帧，然后关闭 TCP 连接。
*   **异常关闭**：底层 TCP 突然中断（RST、超时），没有 Close 帧交换。WebSocket 状态码标记为 1006。

### 4.3 心跳机制：关键的生命线

| 特性 | TCP Keep-Alive (内核) | 应用层心跳 (WebSocket Ping/Pong) |
| :--- | :--- | :--- |
| **默认间隔** | **极长**（约 2 小时） | **可控**（通常 30-60 秒） |
| **探测方式** | 发送空 ACK 探测包 | 发送 Ping 帧（协议标准）或自定义消息 |
| **适用性** | 通用死连接检测 | **WebSocket 实时性必备** |

**为什么必须有心跳？**
如果没有应用层心跳，当网络发生“静默中断”时，连接会变成“僵尸连接”，直到 TCP Keep-Alive 超时（2小时）或中间设备超时（如你遇到的 6 分钟）才会被发现。**心跳能让系统在几十秒内快速感知断网。**

## 五、实战项目经历 (简历版)

### 项目经历：基于 Spring WebSocket 的实时通信系统稳定性优化与异常处理

**背景:**
在公司核心业务的实时通信模块中，负责基于 Spring Boot 的后端服务与浏览器端的 WebSocket 全双工通信。使用 `AbstractWebSocketHandler` 处理连接。

**挑战:**
在用户切换公司 VPN 或安全软件时，后端频繁捕获到 `1006` 异常关闭。观察到两种截然不同的断开行为：
1.  **即时断开**：切换瞬间连接即断。
2.  **“僵尸”连接**：切换后连接未立即断开，而是在长达 **6 分钟** 后才触发关闭（远超最后一条消息的 1.3 分钟间隔），导致大量“僵尸连接”占用资源。

**行动:**
1.  **根因分析**：确认 `1006` 为底层 TCP 异常中断。分析出“6 分钟延迟”是因为网络静默中断且连接空闲，缺失**应用层心跳**，导致无法快速探测连接死亡，只能依赖中间设备的慢速超时。
2.  **引入心跳机制**：实现了双向心跳。客户端每 30 秒发送一次心跳，服务端响应。将异常检测时间从 **6 分钟缩短至 1 分钟以内**。
3.  **增强服务端处理**：在 `afterConnectionClosed` 中针对 `1006` 编写专门清理逻辑；在 `handleTextMessage` 中增加 `session.isOpen()` 检查，解决连接关闭瞬间的“时序竞争”问题。
4.  **完善客户端重连**：基于 `1006` 实现自动重连逻辑，配合指数退避算法，防止网络震荡冲击服务器。

**结果:**
*   解决了网络切换场景下的连接僵死问题，异常连接检测耗时降低 **90%** 以上。
*   有效消除了“僵尸连接”对服务器内存的占用。
*   输出了详细的《WebSocket 异常处理规范》，提升了团队对长连接场景的排查能力。
